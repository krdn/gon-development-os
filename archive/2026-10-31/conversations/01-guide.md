## 작성된 답변

Gon님께는 **ChatGPT Desktop을 중심 작업 화면으로 쓰고, Chat은 판단·설명, Work는 조사·산출물 제작, Codex는 실제 개발에 사용하는 구성**을 추천합니다. **Codex CLI는 Codex를 터미널에서 사용하는 방식**이므로, Desktop의 Codex와 필요에 따라 오가면 됩니다.

먼저 구분해야 할 것은 네 가지입니다.

> **Chat·Work·Codex는 작업 방식, Desktop·웹·CLI는 사용하는 화면, Local·Cloud는 실행 장소, Astra·Sol 등은 AI 모델입니다.**

이 네 가지를 섞으면 “Desktop인데 왜 내 PC 파일을 못 읽지?”, “같은 계정인데 왜 CLI는 앞선 대화를 모르지?”, “Work에서도 개발이 되는데 왜 Codex가 있지?” 같은 혼란이 생깁니다.

아래는 **2026년 10월 31일 확인한 공식 OpenAI 문서 기준**입니다. 현재 문서는 Chat과 Work, Codex를 함께 제공하는 새 ChatGPT Desktop을 기준으로 설명합니다. 실제 표시되는 기능은 앱 버전·운영체제·계정·워크스페이스 설정에 따라 달라질 수 있습니다. :chatgpt-content-reference{index="0"}

## 1. 먼저 전체 구조를 정확히 이해하기

### 1-1. 각각 무엇을 뜻하나?

| 이름 | 정확한 의미 | 선택할 때 생각할 질문 |
|---|---|---|
| **ChatGPT Chat** | 질문하고, 설명을 듣고, 생각을 발전시키는 대화 방식 | “무엇을 알아야 하고, 어떤 판단을 해야 하지?” |
| **ChatGPT Work** | 목표를 맡기고 조사·도구 사용·파일 제작 등을 거쳐 결과물을 받는 작업 방식 | “무엇을 완성해서 받아야 하지?” |
| **Codex** | 저장소·코드·명령·테스트·변경 사항을 다루는 개발 중심 작업 경험 | “어느 프로젝트에서 무엇을 바꾸고 검증해야 하지?” |
| **ChatGPT Desktop** | PC에 설치하는 앱. 현재 Chat·Work·Codex를 제공 | “PC 파일과 도구, 여러 작업을 한 화면에서 다룰까?” |
| **Codex CLI** | 터미널에서 사용하는 Codex 클라이언트 | “현재 개발 폴더에서 바로 작업하거나 스크립트와 연결할까?” |
| **Codex IDE 확장** | 코드 편집기 안에서 사용하는 Codex | “현재 열린 코드와 편집기 문맥을 중심으로 작업할까?” |
| **Codex Cloud** | 준비된 원격 개발 환경에서 Codex 작업을 실행하는 방식 | “내 PC와 독립된 환경에 개발 작업을 맡길까?” |

공식 문서도 Chat은 질문과 논의, Work는 검토 가능한 결과물, Codex는 개발 도구와 기술적인 세부사항을 중심으로 구분합니다. Codex의 앱·CLI·IDE는 공통된 에이전트 실행 체계를 사용하는 서로 다른 인터페이스입니다. :chatgpt-content-reference{index="1"}

예를 들어 다음 두 구성은 모두 가능합니다.

- **ChatGPT Desktop → Work → Cloud → 선택한 모델**
- **ChatGPT Desktop → Codex → This computer → 선택한 모델**

터미널에서는 다음처럼 Codex를 사용합니다.

- **Ubuntu 터미널 → Codex CLI → 현재 프로젝트 폴더 → 선택한 모델**

따라서 “Desktop과 Codex 중 어느 것이 좋은가?”보다는 **“Desktop의 Codex 화면과 터미널의 Codex CLI 중 지금 작업에 어느 쪽이 편한가?”**라고 비교하는 편이 정확합니다.

### 1-2. Work와 Codex는 할 수 있는 일이 상당 부분 겹칩니다

Work는 코드나 명령을 활용해 문서·분석 결과를 만들 수 있고, Codex도 조사·문서·발표자료 같은 작업을 할 수 있습니다.

현재 공식 문서가 강조하는 차이는 다음과 같습니다.

| 비교 항목 | Work | Desktop의 Codex |
|---|---|---|
| 결과를 보여주는 중심 | 완성된 문서·분석·업무 결과 | 코드 변경·실행 결과·개발 상태 |
| 설명 방식 | 일반 업무 언어 중심 | 구현과 기술 세부사항 포함 |
| Git·셸 명령 노출 | 상대적으로 덜 드러냄 | 개발자가 확인하기 쉽게 드러냄 |
| 코드 변경 검토 | 결과 중심 | Diff·Review 화면 제공 |
| 프로젝트 성격 | 자료·문서·업무 맥락 | 코드베이스·개발 작업 |

**차이는 능력의 완전한 분리보다, 어떤 작업을 편하게 지시하고 검토하도록 화면과 소통 방식이 설계됐는지에 있습니다.** :chatgpt-content-reference{index="2"}

## 2. Chat: 이해하고 판단하는 데 사용하기

Chat은 **대화를 통해 문제를 정의하거나, 설명을 듣거나, 선택지를 비교하는 일**에 잘 맞습니다. 웹 검색, 파일 요약, 코드 설명도 여기에 포함됩니다. 긴 설명이나 깊은 분석이 필요하다는 이유만으로 반드시 Work로 옮길 필요는 없습니다. :chatgpt-content-reference{index="3"}

Gon님에게는 다음과 같은 요청이 해당합니다.

- 기존 ASP.NET Core 프로젝트를 유지할지, 신규 서비스에 Rust를 사용할지 판단하기
- EF Core와 Dapper를 어떤 기준으로 나눌지 논의하기
- 낯선 코드나 오류 메시지의 의미를 이해하기
- 아키텍처 대안을 비교하기
- 제품 아이디어의 범위를 좁히기

### 사용 순서

1. **Chat을 선택합니다.**
2. 판단에 필요한 배경과 제약을 알려줍니다.
3. 필요한 코드·문서·이미지를 첨부합니다.
4. 결론의 형식을 지정합니다.
5. 답변에서 모호한 부분을 질문하며 판단을 구체화합니다.

예를 들어 다음처럼 요청할 수 있습니다.

```text
시험지 사진을 문서로 변환하는 서비스를 기획 중이야.

나는 C# 개발 경험이 많고,
이번 신규 프로젝트는 AI가 구현과 유지보수를 많이 담당할 예정이야.

백엔드를 ASP.NET Core로 만드는 경우와 Rust로 만드는 경우를
개발 속도, 운영 복잡도, 장애 대응, 장기 유지보수 기준으로 비교해 줘.

결론을 먼저 제시하고,
내 조건에서 판단을 바꾸게 만드는 요인도 알려줘.
```

이 단계에서 좋은 결과는 **선택의 이유와 전제조건이 명확해지는 것**입니다.

반면 다음 요청은 실제 프로젝트 작업으로 넘어갑니다.

```text
현재 저장소를 열어서 인증 오류를 재현하고,
코드를 수정한 뒤 관련 테스트까지 실행해 줘.
```

이 경우에는 저장소와 개발 도구를 직접 다루기 편한 Codex를 선택하는 것이 좋습니다.

**코드 설명이나 예시를 받은 경우에는, 실제 파일 변경과 빌드·테스트 결과를 별도로 확인하면 됩니다.**

## 3. Work: 완성된 결과물을 받는 데 사용하기

Work는 **목표와 완료 기준을 주고, 여러 단계의 일을 맡기는 방식**입니다. 파일과 연결된 도구를 활용하고, 필요한 자료를 모으고, 결과물을 만들고, 사용자의 수정 요청을 반영하도록 설계되어 있습니다. :chatgpt-content-reference{index="4"}

Gon님에게 적합한 예는 다음과 같습니다.

| 작업 | Work에 맡길 수 있는 결과 |
|---|---|
| 개발 기술 조사 | 출처가 있는 비교 보고서와 권고안 |
| 시험지 사진 정리 | 편집 가능한 문서와 검토용 PDF |
| 신규 서비스 기획 | 요구사항·사용 흐름·개발 범위 문서 |
| 프로젝트 보고 | 진행 현황·문제·다음 작업을 담은 보고서 |
| 여러 자료 취합 | 중복·충돌을 정리한 통합 문서 |
| 반복 업무 | 정해진 주기에 실행하는 조사·점검·업데이트 |

### 3-1. Work에는 무엇을 알려줘야 하나?

복잡한 작업일수록 다음 다섯 가지를 알려주면 좋습니다.

| 항목 | 예시 |
|---|---|
| **목표** | 시험지 사진을 편집 가능한 문서로 변환 |
| **입력 자료** | 첨부한 이미지 10장, 기존 문서 양식 |
| **산출물** | DOCX와 검토용 PDF |
| **완료 기준** | 문항 순서·선택지·표 보존, 판독 불가 표시 |
| **작업 범위** | 원문 복원까지 수행, 해설은 별도 문서로 작성 |

공식 프롬프트 지침도 목표·맥락·출력 형식·작업 범위를 필요한 만큼 제공하도록 권장합니다. 모든 절차를 사용자가 세세하게 지정할 필요는 없습니다. :chatgpt-content-reference{index="5"}

### 3-2. 시험지 변환을 맡기는 예시

```text
첨부한 시험지 사진을 순서대로 읽고,
편집 가능한 DOCX와 검토용 PDF를 만들어 줘.

완료 기준:
- 인쇄된 문제와 선택지를 복원한다.
- 학생이 적은 답과 채점 표시, 낙서는 제외한다.
- 문항 번호와 선택지 순서를 유지한다.
- 표와 그림은 원문의 의미가 유지되도록 배치한다.
- 판독이 어려운 부분은 추측해서 확정하지 말고 표시한다.
- 마지막에 확인이 필요한 부분을 문항 번호별로 정리한다.

문서 생성 후 실제 페이지 배치도 점검해 줘.
```

여기서 중요한 것은 “변환 방법을 알려줘”가 아니라 **“어떤 파일을 어떤 기준으로 완성해 줘”**라고 요청하는 것입니다.

완료 후에도 같은 작업에서 다음처럼 수정할 수 있습니다.

```text
3페이지의 표가 잘렸어.
표를 다음 페이지로 옮기고,
문항과 선택지가 서로 다른 페이지로 나뉘지 않도록 수정해 줘.
```

### 3-3. 개발 기획에도 Work가 잘 맞습니다

```text
첨부한 서비스 아이디어와 참고 화면을 바탕으로
시험지 OCR 서비스의 MVP 명세를 완성해 줘.

포함할 내용:
- 사용자 유형과 주요 사용 흐름
- 1차 출시 범위
- 화면별 기능
- 업로드·처리·실패·재시도 상태
- API 요구사항
- 데이터 보관 정책
- 기능별 완료 기준
- 아직 결정하지 못한 사항

개발자가 그대로 구현 작업을 시작할 수 있는 수준으로 작성해 줘.
```

이런 결과물을 실제 저장소에 전달하면 Codex의 구현 기준으로 사용할 수 있습니다.

## 4. ChatGPT Desktop: 여러 작업을 연결하는 중심 화면

현재 공식 Desktop 안내의 시작 순서는 다음과 같습니다.

1. ChatGPT Desktop을 설치하고 로그인합니다.
2. 새 대화, 프로젝트 또는 로컬 폴더를 선택합니다.
3. 제품 선택 메뉴에서 **ChatGPT 또는 Codex**를 선택합니다.
4. ChatGPT 화면에서는 입력창 위의 **Chat / Work**를 선택합니다.
5. 필요한 자료와 작업 목표를 제공합니다. :chatgpt-content-reference{index="6"}

### Desktop을 중심으로 쓰면 좋은 경우

Gon님처럼 개발과 조사·문서 작업을 함께 하는 경우에는 다음처럼 나누면 편합니다.

| 상황 | Desktop에서 사용할 화면 |
|---|---|
| 설계 방향을 논의할 때 | ChatGPT → Chat |
| 조사 자료를 보고서로 완성할 때 | ChatGPT → Work |
| 실제 프로젝트를 수정할 때 | Codex |
| 코드 변경 내용을 눈으로 검토할 때 | Codex의 Diff·Review |
| 로컬 웹 화면을 확인하며 수정할 때 | Codex와 내장 브라우저 |
| 여러 프로젝트의 작업을 관리할 때 | 프로젝트와 대화 목록 |

이 표는 공식 기능을 바탕으로 한 **제 운영 권장안**입니다. 이미 Codex에서 작업 중이라면 관련 설명서 작성까지 같은 흐름에서 처리해도 됩니다.

### Gon님의 Ubuntu 환경에서 확인할 점

현재 Linux Desktop은 공식 **미리보기 버전**이며, Ubuntu 24.04 LTS와 26.04 LTS 등이 지원 대상으로 명시되어 있습니다. 프로젝트·로컬 파일·Codex 작업을 사용할 수 있습니다. 설치와 업데이트 방법은 [공식 Linux Desktop 안내](https://learn.chatgpt.com/docs/linux/linux-app)에 있습니다. :chatgpt-content-reference{index="7"}

다만 **다른 데스크톱 앱의 화면을 보고 클릭하는 네이티브 Computer Use는 현재 Linux 미리보기에서 지원하지 않습니다.** 공식 지원 대상은 macOS와 Windows입니다. :chatgpt-content-reference{index="8"}

여기서는 기능을 나누어 이해해야 합니다.

- 파일을 읽고 수정하는 기능
- 터미널 명령을 실행하는 기능
- 브라우저와 연결하는 기능
- 다른 데스크톱 앱의 GUI를 조작하는 기능

따라서 Linux에서 네이티브 Computer Use가 없더라도, **파일·코드·터미널 중심 개발과 별도로 지원되는 브라우저 연동은 활용할 수 있습니다.**

## 5. 가장 중요한 구분: 실제 작업은 어디에서 실행되는가?

**Desktop에서 시작했다고 해서 항상 PC에서 실행되는 것은 아닙니다.** 선택한 실행 환경을 확인해야 합니다.

### 5-1. Local과 Cloud 비교

| 실행 방식 | 파일과 도구가 있는 곳 | PC를 꺼도 되는가? | 적합한 작업 |
|---|---|---|---|
| **Work Cloud** | OpenAI가 관리하는 환경, 업로드 자료, 연결된 서비스 | PC에 의존하지 않는 작업은 가능 | 조사·보고서·클라우드 자료 처리 |
| **로컬 Work** | 접근을 허용한 컴퓨터의 파일·도구 | 해당 컴퓨터가 필요 | PC 폴더와 로컬 도구를 사용하는 업무 |
| **Work Cloud + 로컬 컴퓨터 접근** | 클라우드가 작업을 조정하고 로컬 단계는 연결 PC에서 실행 | 로컬 단계에는 온라인 PC 필요 | 기기 간 대화를 이어가면서 PC 자원 활용 |
| **Codex Local** | 선택한 컴퓨터의 프로젝트 폴더 | 실행 컴퓨터가 필요 | 로컬 개발·빌드·테스트 |
| **Codex Worktree** | 같은 컴퓨터의 분리된 Git 작업 디렉터리 | 실행 컴퓨터가 필요 | 독립적인 변경·병렬 개발 |
| **Codex Cloud** | 준비된 원격 개발 환경의 작업별 공간 | 로컬 PC가 잠들어 있어도 가능 | 원격 구현·테스트·PR 준비 |

Work의 로컬 접근과 클라우드 실행은 서로 다른 자원·권한을 사용하며, Codex의 Local과 Worktree는 모두 컴퓨터에서 실행됩니다. Codex Cloud는 작업마다 독립된 작업 공간을 사용합니다. :chatgpt-content-reference{index="9"}

**Worktree는 실행 장소를 클라우드로 바꾸는 기능이 아닙니다.** Git 변경을 분리하는 기능입니다.

### 5-2. 클라우드 경로와 PC 경로를 구분하기

예를 들어 클라우드 작업에서 다음과 같은 경로가 등장했다고 하겠습니다.

```text
/workspace/project
```

이것은 **그 클라우드 실행 환경 안의 경로**입니다.

Gon님의 PC에 다음 폴더가 있다고 해서 자동으로 같은 위치가 되지는 않습니다.

```text
/home/gon/projects/project
```

파일을 이어서 사용하려면 다음과 같은 연결이 필요합니다.

- 파일을 내려받아 로컬 프로젝트에 넣기
- Git 저장소를 통해 변경을 전달하기
- 지원되는 로컬 컴퓨터 연결로 해당 폴더에 접근하기

클라우드 환경은 PC의 파일·프로세스·브라우저 로그인·VPN 접근을 자동으로 물려받지 않습니다. :chatgpt-content-reference{index="10"}

### 5-3. 로컬 DB를 사용하는 개발에서는 특히 중요합니다

Gon님의 PC에서 Docker로 SQL Server나 PostgreSQL을 실행하고 있다면, 로컬 Codex는 필요한 권한과 접속 설정이 있을 때 해당 개발 환경을 사용할 수 있습니다.

반면 클라우드 작업에서 `localhost`에 접속하면 **클라우드 실행 환경 자신**을 가리킵니다. Gon님의 PC를 가리키지 않습니다.

따라서 이런 작업에는 로컬 Codex를 우선 권합니다.

- 현재 PC의 DB로 재현해야 하는 오류
- 로컬 Docker 서비스와 연결된 개발
- 회사 VPN 안의 개발 시스템에 접근해야 하는 작업
- 특정 SDK와 도구가 이미 설치된 개발 환경을 그대로 쓰는 작업

Cloud를 사용할 때는 그 환경에 필요한 의존성·접속 권한·테스트 데이터를 따로 준비하는 편이 좋습니다.

### 5-4. 새 Work 동기화 기능도 “모든 것을 복사”하지는 않습니다

지원되는 계정에서는 Work Cloud가 연결된 PC의 로컬 자원을 사용하면서 대화를 웹·모바일·Desktop에서 이어갈 수 있습니다.

다만 다음 조건이 있습니다.

- PC 파일과 도구가 필요한 단계에서는 PC가 온라인이어야 합니다.
- 기능을 켜기 전의 기존 작업이 자동으로 새 방식으로 바뀌지는 않습니다.
- 적격 작업은 새 턴이 시작될 때 PC를 사용할 수 없으면 클라우드에서 계속할 수 있지만, 그때 PC 자원은 사용할 수 없습니다.
- 로컬에서 실행 중인 턴이 중간에 자동으로 클라우드로 옮겨지는 것은 아닙니다. :chatgpt-content-reference{index="11"}

## 6. Codex CLI: 실제 개발 폴더에서 작업하기

Codex CLI는 **저장소를 읽고, 파일을 수정하고, 설치된 개발 도구를 실행하고, 결과를 검증하는 터미널용 에이전트**입니다.

개발자는 터미널 안에서 탐색·구현·실행·검토를 이어갈 수 있고, `codex exec`를 통해 반복 작업이나 스크립트에도 연결할 수 있습니다. :chatgpt-content-reference{index="12"}

### 6-1. 설치와 시작

Node.js와 npm이 설치되어 있다면 공식 문서에 나온 다음 명령을 사용할 수 있습니다.

```bash
npm install -g @openai/codex@latest
codex --version
```

공식 CLI 안내에는 별도의 독립 설치기도 제공됩니다. 위 npm 설치 명령도 현재 공식 Cookbook에서 확인됩니다. :chatgpt-content-reference{index="13"}

이후 **실제 작업할 프로젝트 폴더**에서 실행합니다.

```bash
cd ~/projects/exam-ocr
codex
```

`~/projects/exam-ocr`는 예시이므로 실제 프로젝트 경로로 바꾸면 됩니다.

처음 실행할 때 로그인하거나, 별도로 다음 명령을 사용할 수 있습니다.

```bash
codex login
```

ChatGPT 로그인은 브라우저 인증 흐름을 사용합니다. :chatgpt-content-reference{index="14"}

### 6-2. 첫 요청은 프로젝트를 파악하게 하는 것이 좋습니다

기존 프로젝트라면 다음처럼 시작할 수 있습니다.

```text
이 저장소를 읽고 개발 환경을 파악해 줘.

확인할 것:
- 주요 프로젝트와 디렉터리 구조
- 빌드·실행·테스트 방법
- 핵심 의존성
- 현재 변경 중인 파일
- 적용되는 프로젝트 지침

이후 인증 오류 수정 작업을 할 예정이므로,
관련 코드의 진입점도 찾아줘.
```

그다음 실제 작업을 맡깁니다.

```text
로그인 후 간헐적으로 발생하는 500 오류를 재현하고 수정해 줘.

기존 API 응답 형식과 인증 정책은 유지해 줘.
문제와 관련된 검증을 실행하고,
완료되면 변경 파일, 원인, 검증 결과,
아직 확인하지 못한 사항을 정리해 줘.
```

Gon님처럼 경험이 많은 개발자는 구현 과정을 한 줄씩 지시하기보다 **변경 범위·유지해야 할 계약·완료 증거**를 명확히 주는 편이 효율적입니다.

### 6-3. 셸 명령과 Codex 내부 명령은 구분합니다

다음은 **일반 터미널에서** 실행하는 명령입니다.

| 명령 | 용도 |
|---|---|
| `codex` | 대화형 Codex 시작 |
| `codex -C /path/to/project` | 작업 폴더를 지정해 시작 |
| `codex resume` | 저장된 대화 선택 후 재개 |
| `codex resume --last` | 현재 폴더의 가장 최근 대화 재개 |
| `codex review --uncommitted` | 아직 커밋하지 않은 변경 검토 |
| `codex review --base main` | 지정한 기준 브랜치와 비교해 검토 |
| `codex exec "요청 내용"` | 비대화형 작업 실행 |

`--base main`의 `main`은 실제 저장소의 기준 브랜치로 바꾸면 됩니다. :chatgpt-content-reference{index="15"}

다음은 **Codex가 실행된 뒤 그 입력창에서** 사용하는 명령입니다.

| 명령 | 용도 |
|---|---|
| `/status` | 모델·권한·작업 범위·문맥 사용 상태 확인 |
| `/model` | 모델과 지원되는 추론 수준 선택 |
| `/plan` | 계획 모드로 전환 |
| `/permissions` | 작업 권한 설정 |
| `/diff` | 변경 사항 확인 |
| `/review` | 코드 변경 검토 |
| `/init` | 현재 폴더의 `AGENTS.md` 초안 생성 |
| `/skills` | 사용할 스킬 선택 |
| `/mcp` | 현재 연결된 MCP 도구 확인 |
| `/resume` | 저장된 대화 재개 |
| `/new` | 새 대화 시작 |

이 명령들은 일반 ChatGPT 웹 입력창에서 모두 같은 방식으로 작동하는 명령이 아닙니다. CLI에서는 `/`를 입력하면 현재 버전에서 사용할 수 있는 명령 목록을 확인할 수 있습니다. :chatgpt-content-reference{index="16"}

### 6-4. 긴 작업을 목표 중심으로 진행하기

지원되는 Codex 버전에서는 `/goal`로 지속적인 목표를 줄 수 있습니다.

```text
/goal docs/SPEC.md의 업로드 API를 구현하고,
정의된 정상·오류 시나리오 검증을 통과시켜 줘.
완료 조건을 만족할 때까지 필요한 수정과 검증을 진행해 줘.
```

Goal은 작업 목표를 유지하면서 다음 행동을 선택하도록 돕습니다. 성공뿐 아니라 중단·한도·해결이 필요한 차단 요인 등으로 멈출 수도 있으므로, **검증할 수 있는 완료 기준**이 중요합니다. :chatgpt-content-reference{index="17"}

### 6-5. CLI 설치와 모델 실행은 별개입니다

Codex CLI를 PC에 설치하면 주로 **파일 접근과 명령 실행을 담당하는 에이전트 실행 체계**가 설치됩니다.

일반적인 OpenAI 모델 사용과 PC에서 모델 자체를 실행하는 구성은 구분해야 합니다. 로컬 모델을 사용하는 별도 구성은 `--oss`와 Ollama·LM Studio 같은 로컬 제공자를 통해 설정하도록 문서화되어 있습니다. :chatgpt-content-reference{index="18"}

## 7. Desktop의 Codex와 Codex CLI는 어떻게 함께 쓰나?

두 가지를 모두 사용할 때는 **파일, 설정, 대화의 공유 범위를 각각 확인**하면 됩니다.

### 7-1. 가장 확실한 통합은 같은 저장소를 사용하는 것입니다

예를 들어 Desktop에서 다음 폴더를 프로젝트로 열었다면,

```text
/home/gon/projects/exam-ocr
```

CLI에서도 같은 폴더에서 실행합니다.

```bash
cd /home/gon/projects/exam-ocr
codex
```

그러면 두 인터페이스는 같은 실제 파일을 대상으로 작업할 수 있습니다.

다만 둘 중 하나가 Worktree를 사용한다면 실제 작업 디렉터리가 달라집니다. 이때는 **저장소 이름뿐 아니라 현재 경로와 브랜치도 확인**해야 합니다. Worktree는 변경을 분리하기 위한 기능입니다. :chatgpt-content-reference{index="19"}

실무에서는 이렇게 나누는 것을 권합니다.

- **Desktop Codex:** 변경 사항과 화면을 살펴보며 작업 방향을 조정
- **Codex CLI:** 터미널에서 구현·검증·로그 분석·반복 명령 수행
- **IDE:** 코드를 직접 읽고 수정하면서 세부 검토

같은 파일을 여러 에이전트가 동시에 수정하도록 맡기기보다는, 작업을 순차적으로 이어가거나 독립적인 Worktree로 나누는 편이 관리하기 쉽습니다.

### 7-2. 공통 설정을 사용할 수 있습니다

로컬 Codex의 앱·CLI·IDE는 공통 설정 체계를 사용합니다.

대표적인 파일은 다음과 같습니다.

```text
~/.codex/config.toml
```

프로젝트별 설정은 신뢰한 프로젝트의 다음 위치에 둘 수 있습니다.

```text
.codex/config.toml
```

이 설정에는 모델·권한·MCP 등 개발 에이전트의 동작 설정이 포함됩니다. 다만 명령행 옵션이나 프로젝트 설정이 적용되어 실제 값이 달라질 수 있으므로 `/status`로 현재 상태를 확인하면 좋습니다. :chatgpt-content-reference{index="20"}

### 7-3. Desktop과 IDE 사이에는 공식 대화 연동이 있습니다

공식 문서는 **Desktop 앱과 IDE 확장에서 같은 프로젝트를 열면 활성 대화와 편집기 문맥을 공유할 수 있다**고 설명합니다.

Desktop의 **IDE context**를 켜면 편집기에 열린 파일 등의 문맥을 사용할 수 있으며, 앱 대화를 IDE에서 열거나 IDE 대화를 앱에서 계속할 수 있습니다. :chatgpt-content-reference{index="21"}

### 7-4. CLI에서 Desktop으로 같은 대화를 여는 기능도 있습니다

CLI의 `/app`은 현재 대화를 Desktop에서 이어가는 기능입니다.

```text
/app
```

다만 현재 공식 CLI 문서는 이 경로를 **macOS·Windows 대상으로 안내**합니다. Ubuntu에서 동일하게 동작한다고 전제하기보다는, 해당 버전의 지원 여부를 확인하고 같은 저장소·명세·작업 상태를 기준으로 연결하는 방식을 기본으로 삼는 것이 좋습니다. :chatgpt-content-reference{index="22"}

## 8. Chat·Work에서 Codex로 작업을 넘기는 방법

여기서 가장 주의할 점은 다음입니다.

**같은 계정으로 로그인하는 것, 같은 파일을 사용하는 것, 같은 대화 맥락을 사용하는 것은 각각 별개입니다.**

### 8-1. 무엇이 공유되고, 무엇은 별도인가?

| 항목 | 이해해야 할 범위 |
|---|---|
| ChatGPT 프로젝트 | 관련 대화·업로드 파일·지침·연결 자료를 묶음 |
| 로컬 프로젝트 | 실제 컴퓨터 폴더에 접근할 수 있도록 연결 |
| CLI 프로젝트 | CLI를 시작한 디렉터리 또는 지정한 작업 디렉터리 |
| 대화 동기화 | 로컬 폴더 전체가 다른 기기로 복사되는 기능은 아님 |
| Work와 Codex 기록 | 별도의 대화 기록 |
| 대화 재개 | 현재 파일 상태를 읽으며 이어감. 과거 파일 상태 복원과는 별개 |

ChatGPT 프로젝트와 로컬 프로젝트는 역할이 다릅니다. 일반 ChatGPT 프로젝트를 만든 것만으로 PC 폴더에 직접 접근할 수 있는 것은 아닙니다. :chatgpt-content-reference{index="23"}

### 8-2. 기존 ChatGPT 대화를 Codex에 추가하는 경로

공식 문서에는 Codex의 **Quick chat / New chat에서 기존 ChatGPT 대화를 열어 Codex 대화에 추가하는 기능**이 안내되어 있습니다.

해당 기능이 화면에 제공되면 앞선 논의를 전달하는 데 사용할 수 있습니다. 다만 이를 모든 Work 파일·메모리·도구 상태까지 완전히 이전하는 기능으로 이해해서는 안 됩니다. :chatgpt-content-reference{index="24"}

### 8-3. 개발에서는 명세와 현재 상태를 남기는 방식이 가장 안정적입니다

제가 권하는 인계 방식은 다음과 같습니다.

| 전달할 내용 | 예시 |
|---|---|
| 목표 | 시험지 업로드 후 처리 상태를 확인할 수 있게 만들기 |
| 확정한 결정 | 지원 형식, 인증 방식, 1차 개발 범위 |
| 작업 위치 | 저장소·브랜치·디렉터리 |
| 완료 기준 | 정상·오류 시나리오와 검증 방법 |
| 현재 상태 | 완료한 기능, 실패 중인 테스트, 다음 작업 |
| 주요 자료 | 설계 문서·화면·API 계약·참고 링크 |

작은 프로젝트라면 처음부터 문서를 많이 만들 필요는 없습니다.

- `AGENTS.md`: 프로젝트에서 지켜야 할 개발 규칙
- `docs/SPEC.md`: 구현할 요구사항과 완료 기준
- `docs/STATUS.md`: 완료·진행·차단 상태

정도로 시작해도 충분합니다.

여기서 **`AGENTS.md`는 Codex가 자동으로 찾아 읽는 지침 파일**입니다. `SPEC.md`나 `STATUS.md` 같은 임의의 문서는 요청에서 지정하거나 `AGENTS.md`에 읽도록 안내해 두는 편이 좋습니다. :chatgpt-content-reference{index="25"}

Chat이나 Work에서 다음처럼 인계 자료를 요청할 수 있습니다.

```text
지금까지 결정한 내용을 Codex 구현 작업용으로 정리해 줘.

포함할 내용:
- 구현 목표
- 확정된 결정과 아직 열린 문제
- 입력·출력과 API 계약
- 작업 순서
- 기능별 완료 기준
- 검증 방법
- 다음 작업자가 바로 시작할 첫 작업

추측이나 검토 중인 내용은 확정 사항과 구분해 줘.
```

Codex에서는 다음처럼 이어갑니다.

```text
AGENTS.md와 docs/SPEC.md, docs/STATUS.md를 읽고
현재 저장소 상태와 일치하는지 확인해 줘.

그다음 미완료 작업 중 첫 번째 항목을 구현하고 검증해 줘.
완료되면 STATUS.md에 실제 결과를 반영해 줘.
```

이 방식은 인터페이스나 모델을 바꾸더라도 작업의 기준을 유지하기 쉽습니다.

## 9. Gon님의 프로젝트에 적용한 구체적인 통합 예시

다음은 **시험지 OCR 서비스 개발을 위한 제 권장 운영 예시**입니다.

### 단계 1. Chat에서 제품 범위를 결정합니다

```text
시험지 사진을 업로드하면
편집 가능한 문서와 풀이 초안을 만드는 서비스를 만들려고 해.

첫 출시에서 꼭 필요한 기능을 정리하고,
정확도와 개발 난이도를 고려해 2차로 미룰 기능을 골라줘.

사용자가 결과를 검토하고 수정하는 과정까지 포함해 줘.
```

이 단계에서는 다음을 결정합니다.

- 누가 사용하는가
- 어떤 자료를 넣는가
- 어떤 결과를 받는가
- 어디까지 자동화할 것인가
- 사용자 검토가 필요한 지점은 어디인가

기술 선택도 이 단계에서 논의할 수 있습니다. 이미 스택을 정했다면 그 선택을 전제로 진행하면 됩니다.

### 단계 2. Work에서 구현 가능한 명세로 만듭니다

```text
확정한 MVP 범위를 바탕으로 구현 명세를 작성해 줘.

업로드, 처리 대기, 처리 중, 완료, 실패, 재시도 흐름을 포함하고,
각 화면과 API가 어떤 상태를 처리해야 하는지 명시해 줘.

기능별 완료 기준과 대표적인 오류 사례도 작성해 줘.
```

이 단계의 결과는 개발자가 사용할 수 있는 **명세와 검증 기준**입니다.

문서가 만들어졌다면 중요한 내용을 읽어보고, 모순이나 누락을 수정합니다. 구현 도중 제품 정책을 계속 다시 결정하지 않도록 핵심 규칙부터 확정하는 것이 좋습니다.

### 단계 3. Desktop Codex에서 저장소를 열고 첫 기능을 구현합니다

```text
이 프로젝트에 시험지 이미지 업로드 기능을 구현해 줘.

docs/SPEC.md의 요구사항을 기준으로 작업하고,
기존 프로젝트 구조와 코딩 규칙을 따라줘.

완료 기준:
- 허용된 형식의 파일을 업로드할 수 있다.
- 크기 제한과 잘못된 형식을 처리한다.
- 업로드 결과가 저장되고 조회된다.
- 실패 시 사용자가 원인을 알 수 있다.
- 관련 검증 결과를 제시한다.
```

여기서는 실제 코드와 파일이 만들어지고, 실행 결과를 확인합니다.

### 단계 4. CLI에서 구현·검증을 집중적으로 이어갑니다

터미널에서 같은 프로젝트를 열고 다음처럼 요청합니다.

```text
현재 업로드 처리 코드와 실패 로그를 확인해 줘.

동일 파일을 재시도할 때 중복 작업이 생성되는지 재현하고,
명세에 맞게 수정해 줘.

기존 정상 동작을 유지하는지 확인하고,
수정한 부분과 검증 결과를 정리해 줘.
```

이런 작업은 터미널 로그·테스트·코드 탐색을 함께 사용하는 CLI 흐름에 잘 맞습니다.

### 단계 5. Desktop에서 실제 화면을 검토합니다

내장 브라우저로 로컬 앱을 확인할 수 있는 환경이라면 다음처럼 요청합니다.

```text
실행 중인 업로드 화면에서 다음 흐름을 확인해 줘.

- 정상 파일 업로드
- 허용되지 않은 파일 업로드
- 처리 실패 후 재시도
- 처리 중 새로고침
- 모바일 너비에서 결과 확인

문제가 발견되면 원인을 찾아 수정하고,
어떤 흐름을 확인했는지 알려줘.
```

Desktop의 내장 브라우저는 웹사이트와 로컬 웹 앱을 함께 보면서 검토하는 용도로 제공됩니다. :chatgpt-content-reference{index="26"}

### 단계 6. Work에서 설명서와 보고 자료를 만듭니다

```text
이번에 완료한 기능과 검증 결과를 바탕으로
사용자 안내서와 개발 완료 보고서를 만들어 줘.

실제로 구현한 기능만 포함하고,
미완료 항목과 알려진 제한은 구분해 줘.
```

여기까지가 한 번의 개발 단위입니다.

**이미 요구사항이 명확한 버그 수정은 바로 Codex에서 시작하면 됩니다.** 반대로 조사 보고서 하나가 목표라면 Work에서 완료하면 됩니다. 작업의 성격에 맞게 필요한 단계를 선택하는 것이 제 권장 방식입니다.

## 10. 스킬·설정·메모리는 어떻게 통합해야 하나?

Gon님이 만든 `gon-web-engineering` 같은 스킬을 여러 환경에서 쓰려면 이 구분이 중요합니다.

### 10-1. 설정·지침·스킬은 역할이 다릅니다

| 구분 | 역할 | 대표 위치 |
|---|---|---|
| **Codex 설정** | 모델·권한·MCP 등 실행 방식 | `~/.codex/config.toml` |
| **개인 공통 지침** | 여러 저장소에서 적용할 작업 원칙 | `~/.codex/AGENTS.md` |
| **프로젝트 지침** | 해당 프로젝트의 구조·검증·코드 규칙 | 저장소의 `AGENTS.md` |
| **개인 로컬 스킬** | 여러 프로젝트에서 재사용할 작업 절차 | `~/.agents/skills/` |
| **프로젝트 스킬** | 저장소와 함께 관리할 작업 절차 | `.agents/skills/` |
| **플러그인** | 스킬·연결 도구 등을 설치 가능한 형태로 배포 | 지원되는 플러그인 디렉터리 |

Codex는 전역과 프로젝트의 `AGENTS.md` 지침을 조합하며, 로컬 스킬은 개인·저장소 등의 정해진 위치에서 찾습니다. :chatgpt-content-reference{index="27"}

예를 들면 다음과 같습니다.

- **설정:** 기본 모델과 MCP 서버를 지정
- **지침:** 기존 프로젝트의 기술 선택과 테스트 규칙을 준수
- **스킬:** 신규 웹 프로젝트를 구성할 때 정해진 절차를 적용

스킬은 이름·설명·작업 지침·참고 자료 등을 묶은 재사용 가능한 절차입니다. 플러그인은 여기에 MCP 연결 같은 도구를 포함해 배포할 수 있습니다. :chatgpt-content-reference{index="28"}

### 10-2. `gon-web-engineering`을 사용할 때

해당 환경에 스킬이 설치되어 있다면 Codex에서는 다음처럼 명시적으로 요청할 수 있습니다.

```text
$gon-web-engineering

이 저장소의 현재 구성을 먼저 확인하고,
신규 기능 구현에 해당하는 지침을 적용해 줘.
```

ChatGPT에서는 `@` 선택 메뉴를 통해 설치된 스킬이나 플러그인을 지정할 수 있습니다. Codex에서는 `$` 스킬 참조를 지원합니다. :chatgpt-content-reference{index="29"}

다만 **웹 Work에서 사용할 수 있는 스킬과 PC의 로컬 스킬 폴더가 같은 저장 위치인지는 별도로 확인해야 합니다.**

공식 문서는 다음 용도를 구분합니다.

- 직접 스킬 폴더: 로컬 작성·저장소 단위 사용
- 플러그인 패키지: 여러 환경이나 사용자에게 재사용 가능한 형태로 배포

따라서 Gon님의 스킬은 **Git으로 원본을 관리하고, 사용할 환경에 맞게 로컬 스킬 또는 플러그인으로 설치하는 방식**을 권합니다. :chatgpt-content-reference{index="30"}

### 10-3. ChatGPT 메모리와 Codex 메모리도 별도입니다

현재 공식 문서는 다음과 같이 설명합니다.

- Work는 계정·워크스페이스의 **ChatGPT 메모리 설정**을 사용합니다.
- 로컬 Codex 클라이언트는 **별도의 로컬 메모리 저장소와 제어 기능**을 사용합니다.
- 필수 규칙은 메모리에만 의존하지 않고 `AGENTS.md`나 저장소 문서에 두도록 권장합니다. :chatgpt-content-reference{index="31"}

따라서 Gon님이 중요하게 생각하는 규칙은 다음처럼 관리하는 편이 좋습니다.

| 정보 성격 | 권장 위치 |
|---|---|
| 개인적인 대화 선호 | ChatGPT 개인 설정·메모리 |
| 프로젝트에서 꼭 지킬 규칙 | `AGENTS.md` |
| 제품 요구사항 | 명세 문서 |
| 반복 작업 방식 | 스킬 |
| 현재 구현 상태 | 작업 상태 문서·이슈·PR |
| 코드의 실제 상태 | Git 저장소 |

이 구성에서는 모델이 바뀌어도 프로젝트의 중요한 기준을 다시 전달하기 쉽습니다.

## 11. 브라우저·연결 앱·예약 작업은 어떻게 나누나?

### 11-1. 브라우저는 세 가지를 구분하면 됩니다

| 방식 | 주로 사용하는 상황 | 로그인 상태 |
|---|---|---|
| **Desktop 내장 브라우저** | 로컬 웹 앱 확인, 사이트 작업, 시각적 검토 | 일반 브라우저와 별도 프로필 |
| **브라우저 확장 연결** | 기존 Chrome 등의 열린 탭과 로그인된 사이트 사용 | 연결한 기존 브라우저 문맥 활용 |
| **Work 클라우드 브라우저** | 클라우드에서 사이트를 조사하거나 작업 | 클라우드 브라우저 자체 세션 |

Desktop 내장 브라우저는 기존 브라우저의 탭과 세션을 자동으로 공유하지 않습니다. 기존 Chrome 등의 로그인 상태가 필요한 작업에는 브라우저 확장 연결이 별도로 제공됩니다. Work 클라우드 브라우저도 PC 브라우저와 독립된 세션을 사용합니다. :chatgpt-content-reference{index="32"}

예를 들어 다음처럼 **어느 브라우저를 사용할지 요청에 명시**하면 혼동을 줄일 수 있습니다.

```text
연결된 Chrome의 현재 로그인된 관리자 페이지에서
주문 목록을 확인해 줘.
```

```text
Desktop 내장 브라우저에서 실행 중인 로컬 웹 앱을 열고
업로드 화면을 확인해 줘.
```

참고로 Desktop의 내장 Browser 화면은 CLI나 IDE 확장에 동일하게 제공되지 않습니다. CLI에서 사용할 수 있는 외부 도구는 별도의 연결과 설정에 따라 달라집니다. :chatgpt-content-reference{index="33"}

### 11-2. 연결 앱은 자료와 행동에 접근하는 통로입니다

예를 들어 Google Drive·GitHub·메일 등의 플러그인을 연결하면, 해당 서비스의 자료와 도구를 사용할 수 있습니다.

요청할 때는 다음처럼 출처를 구체화하는 편이 좋습니다.

```text
@GitHub에서 이 프로젝트의 최근 PR과 열린 이슈를 확인하고,
다음 릴리스에 포함할 작업을 정리해 줘.
```

단, 이름을 언급하는 것만으로 연결이나 권한이 생기지는 않습니다. 실제로 설치·연결된 플러그인과 그 권한 안에서 작업합니다. :chatgpt-content-reference{index="34"}

### 11-3. 정기 실행과 긴 작업은 구분합니다

| 목적 | 적합한 방법 |
|---|---|
| 지금 시작한 기능을 완료할 때까지 진행 | 일반 작업 지시 또는 지원되는 Codex Goal |
| 매일·매주 정해진 시간에 실행 | Scheduled 작업 |
| 개발 스크립트나 CI에서 실행

> 원본 응답 일부가 조회 도구 길이 제한으로 생략되었습니다.
