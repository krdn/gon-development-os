## 1\. 최종 권장 방식

앞으로 앱, 웹서비스, 스킬, AI 에이전트, CLI 도구 등 모든 신규 프로젝트는 **ChatGPT Work + Codex + GitHub + Skills를 결합한 통합 개발 워크플로우**로 진행하는 것을 권장합니다.

핵심은 **사용자는 목표와 최종 결과를 결정하고, AI가 기획·설계·개발·테스트·검토·배포 준비를 수행하는 구조**입니다.

단순히 바이브 코딩으로 빠르게 코드를 생성하는 방식이 아니라, 장기적으로 유지보수하고 개선할 수 있는 소프트웨어 엔지니어링 체계입니다.

권장 전체 아키텍처

**사용자 — Product Owner**

목표 제시 · 핵심 의사결정 · 최종 승인

**Chat**

아이디어 · 요구사항 · 기술 의사결정

**Work**

리서치 · 설계 산출물 · 다단계 업무 실행

명세와 작업 계약을 Git에 기록

**Codex / Codex CLI**

코딩 · 실행 · 테스트 · 디버깅 · 리팩터링

필요한 경우 독립 워커에 작업 위임

**GitHub + CI/CD**

PR · 코드 리뷰 · 자동 품질 검증 · 릴리스

**완료 · 배포 · 운영**

승인된 릴리스 · 모니터링 · 개선 작업

프로젝트 경험 → 재사용 스킬 및 개발 표준 개선

이 구성에서 가장 중요한 설계 원칙은 **Chat과 Work가 개발 방향을 정하고, Codex가 실제 소스코드 변경을 책임지며, GitHub가 공식 작업 상태를 보존한다**는 것입니다.

ChatGPT의 Work와 Codex가 모든 작업을 자동으로 상호 전달하는 하나의 에이전트는 아닙니다. 따라서 Git 저장소의 명세, 작업 계획, 커밋, PR을 통해 두 환경을 연결해야 합니다.

## 3\. 프로젝트 시작부터 완료까지의 표준 프로세스

모든 개발에 동일한 10단계를 적용하되, 프로젝트 규모에 따라 필요한 산출물과 검증 수준을 조정합니다.

**표준 개발 단계** 10단계 · 4개 품질 게이트

### 단계별 자동 진행 원칙

프로젝트가 시작되면 AI는 작은 기능부터 실제로 동작하는 결과물을 만들고, 테스트 결과를 확인하면서 다음 단계로 진행합니다.

예를 들어 웹 애플리케이션을 개발할 때 전체 화면을 먼저 생성하는 대신 다음과 같은 순서가 좋습니다.

`실행 가능한 서버 → 첫 번째 API → DB 연결 → 첫 번째 UI → 통합 테스트 → 기능 확장`

이를 **Vertical Slice 방식**이라고 합니다. 하나의 기능을 프론트엔드부터 데이터베이스까지 완성하여 전체 구조가 실제로 작동하는지 조기에 확인합니다.

장기 프로젝트에는 계획, 코드 변경, 실행 결과, 문제 수정, 문서 갱신을 반복하는 Codex의 개발 루프가 적합합니다. citeturn435682search5turn435682search2

## 4\. AI 모델과 추론 수준의 권장 배치

모든 작업을 최고 성능 모델로 처리하는 것은 권장하지 않습니다. 중요한 것은 난이도와 실패 위험에 따라 모델을 다르게 사용하는 것입니다.

| 업무 | 권장 모델 | 추론 수준 |
|--------|--------|--------|
| 복잡한 아키텍처, 핵심 설계 | GPT-6 Astra | High 이상 |
| 중요한 보안·성능·설계 검토 | GPT-6 Astra | High / 최대 수준 |
| 일반적인 기능 구현 | GPT-6.1 Sol | Medium / High |
| 버그 수정, 리팩터링 | GPT-6.1 Sol | Medium / High |
| UI 시각 검토, 화면 조작 | GPT-6.1 Terra | Medium |
| 단순 분석, 반복 작업 | GPT-6 Luna | Low / Medium |
| 최종 통합 판단 | GPT-6 Astra | High |

공식 모델 문서에서도 Astra는 고난도 추론과 소프트웨어 엔지니어링에, Sol은 성능·속도·비용의 균형에, Terra는 시각적 추론과 컴퓨터 조작에 적합한 모델로 설명합니다. citeturn723519search3turn609080view1

이것은 고정된 모델 구성보다 **작업 난이도 기반 모델 라우팅 정책**으로 유지하는 편이 좋습니다. 새 모델이 출시되면 대표 프로젝트의 테스트와 성능을 비교한 뒤 기존 모델을 교체합니다.

또한 실패가 발생했을 때는 무조건 모델을 업그레이드하지 않습니다. 먼저 재현 조건과 로그를 확보하고, 같은 모델로 수정할 수 없거나 복잡한 구조적 판단이 필요한 경우 고성능 모델로 에스컬레이션합니다.

## 5\. 가장 중요한 기반: GitHub를 공식 기록 저장소로 사용

ChatGPT의 대화 메모리와 Codex의 작업 세션만으로 장기 프로젝트를 관리하면 컨텍스트가 흩어질 수 있습니다.

따라서 **소스코드, 결정, 작업 상태, 테스트 명령과 결과는 GitHub 저장소를 기준으로 관리**하는 방식을 권장합니다.

### 권장 프로젝트 구조

```text

my-project/
├── AGENTS.md
├── README.md
├── docs/
│   ├── PRODUCT.md
│   ├── ARCHITECTURE.md
│   ├── PLAN.md
│   ├── STATE.md
│   └── decisions/
├── .agents/
│   └── skills/
├── .github/
│   └── workflows/
│       └── ci.yml
├── src/
├── tests/
├── scripts/
└── docker-compose.yml  # 필요 시
```

모든 프로젝트에 모든 파일을 강제할 필요는 없습니다. 작은 CLI 도구나 스킬은 `README.md`, `AGENTS.md`, 테스트 파일만으로 시작할 수 있습니다.

| 파일 | 역할 |
|--------|--------|
| `AGENTS.md` | 에이전트가 항상 따라야 할 최소 규칙 |
| `PRODUCT.md` | 무엇을 왜 만드는지, 완료 기준 |
| `ARCHITECTURE.md` | 기술 구성과 중요한 설계 결정 |
| `PLAN.md` | 마일스톤 및 실행 순서 |
| `STATE.md` | 현재 진행 상태와 다음 작업 |
| `decisions/` | 변경 이력이 필요한 주요 기술 결정 |
| `.agents/skills/` | 해당 프로젝트 전용 스킬 |
| `.github/workflows/` | 자동 빌드·테스트·검증 |

특히 `STATE.md`는 대화가 바뀌어도 개발을 이어갈 수 있도록 하는 간단한 체크포인트로 활용합니다. 이슈와 PR을 상세 작업 원장으로 사용하고, `STATE.md`에는 현재 마일스톤, 마지막 검증 결과, 차단 요인, 다음 작업만 기록하여 중복 관리를 방지합니다.

`AGENTS.md`는 작고 간결하게 유지합니다. Codex가 항상 읽는 파일이므로 상세한 개발 절차는 Skills나 참조 문서로 분리하는 것이 좋습니다. OpenAI의 최신 지침 역시 지나치게 긴 `AGENTS.md`와 불필요한 스킬 설명이 성능을 떨어뜨릴 수 있다고 설명합니다. citeturn435682search0turn609080view3

## 6\. 모든 프로젝트에 적용할 공통 Skill 만들기

이 부분은 앞으로 개발 효율성을 결정할 가장 중요한 작업입니다.

기존에 만든 `gon-web-engineering` 스킬은 웹 개발 기술 표준으로 활용하고, 그 위에 프로젝트 전체 생명주기를 관리하는 상위 스킬을 추가하는 구성을 추천합니다.

**gon-project-lifecycle**

모든 프로젝트의 시작·실행·검증·완료 기준

**gon-web-engineering**

앱·웹·API 개발 표준

**gon-skill-engineering**

Skill 제작·검증 표준

**gon-agent-engineering**

에이전트·도구·평가 표준

**gon-quality-release**

공통 검증·배포 표준

다만 처음부터 스킬 네다섯 개를 모두 구현할 필요는 없습니다.

우선 `gon-project-lifecycle` 하나를 만들고, 기존 `gon-web-engineering`과 연결해 실제 프로젝트에서 검증합니다. 에이전트나 스킬 개발이 반복될 때만 전문 스킬을 추가하는 점진적 확장 방식이 더 효율적입니다.

### Ubuntu에서의 설치 위치

Codex CLI가 사용하는 전역 개인 스킬의 표준 위치는 다음과 같습니다.

`~/.agents/skills/gon-project-lifecycle/SKILL.md`

Codex의 전역 지침은 다음 위치를 사용합니다.

`~/.codex/AGENTS.md`

GitHub 저장소별 지침은 저장소 루트의 `AGENTS.md`로 관리합니다.

스킬은 Codex CLI·데스크톱·IDE 확장에서 활용할 수 있습니다. ChatGPT 웹과 모바일의 Chat·Work까지 통합 배포하려면 플러그인으로 패키징하는 방식이 적합합니다. **Work 내부에서 생성한 스킬이 Ubuntu 로컬 파일시스템에 자동으로 설치된다고 가정해서는 안 됩니다.** citeturn723519search2turn723519search0

# 신규 프로젝트 전체 개발 실행

다음 프로젝트를 **Gon AI Development OS 표준 워크플로우**에 따라 기획부터 검증 및 배포 준비까지 수행한다.

**프로젝트:** [만들고 싶은 앱, 스킬, 에이전트에 대한 설명]

**작업 정책**

1. 프로젝트 유형과 목표를 분석하고, 필요한 경우 최신 기술 및 라이브러리를 조사한다.
2. 요구사항, MVP, 비기능 요구사항, 성공 기준과 완료 조건을 수립한다.
3. 기술 스택과 아키텍처를 비교하여 합리적인 대안을 선택하고 결정 이유를 기록한다.
4. GitHub를 공식 기록 저장소로 사용하며, 재현 가능한 개발 환경을 구성한다.
5. 구현은 Codex가 수행하도록 실행 가능한 작업 명세를 준비한다.
6. 구현·테스트·오류 수정·리팩터링·리뷰를 반복하여 완료 조건을 만족시킨다.
7. 작업 상태, 주요 설계 결정, 테스트 결과, 남은 위험을 영속적으로 기록한다.
8. 배포 준비, 운영 문서, 롤백 절차까지 작성한다.
9. 반복적인 실행 절차는 스킬로 개선하되 불필요한 스킬과 지침을 추가하지 않는다.
10. 사소한 의사결정은 합리적으로 판단하여 계속 진행하고, 보안·비용·외부 권한·파괴적 작업·운영 배포 등 중요한 승인 사항에서만 사용자에게 확인한다.

**완료 조건**

- 실제로 실행되는 결과물이 있어야 한다.
- 정해진 자동 테스트와 품질 기준을 충족해야 한다.
- 실패한 검증이나 미완료 작업을 숨기지 않는다.
- README, 설치·운영 방법, 변경 사항과 남은 제한 사항을 제공한다.
- 사용자가 최종 결과를 평가할 수 있는 검증 방법을 제공한다.

진행 상태는 GitHub와 프로젝트 문서에 남기고, 도구 또는 권한 제약으로 실행할 수 없는 작업은 명확히 표시한다.

### 두 번째: Codex에서 실제 개발

설계와 작업 명세가 준비되면 Codex 또는 Codex CLI로 구현을 진행합니다.

Ubuntu의 기존 개발 저장소라면 다음처럼 시작할 수 있습니다.

```bash

cd ~/projects/my-project
codex
```

이후 Codex에 프로젝트의 `PLAN.md`와 GitHub 이슈에 따라 구현하도록 지시합니다. 공통 스킬이 설치되어 있다면 `$gon-project-lifecycle`을 명시적으로 호출할 수도 있습니다.

여기서 중요한 점은 다음과 같습니다.

- **로컬 Codex CLI\:** 현재 Ubuntu의 소스코드, Docker, 설치된 SDK, 로컬 데이터베이스를 사용하는 개발에 적합합니다.
- **Codex Cloud\:** GitHub 저장소 및 클라우드 개발 환경을 설정한 후 독립 작업을 실행할 때 적합합니다.
- **ChatGPT Work\:** 설계·리서치·결과 정리·브라우저 및 외부 도구 작업에 적합합니다.

Codex Cloud는 컴퓨터를 종료해도 작업을 계속 수행할 수 있지만, 로컬의 미커밋 변경 내용을 자동으로 공유하지는 않습니다. 작업 환경을 정확히 구분하고 중요한 결과를 커밋해야 합니다. citeturn723519search9turn607450search3

### 세 번째: 구현 결과를 Work에서 종합 검토

Codex의 PR과 테스트 결과가 준비되면 Work에서 요구사항 및 설계와 비교해 누락된 기능을 점검합니다.

검토 결과 수정이 필요하면 다시 Codex 작업으로 연결합니다. 자동으로 반영할 수 없는 단계에서는 PR 링크, 이슈, 저장소 파일 등의 명시적인 인계 자료를 사용합니다.

이 과정이 안정화되면 GitHub Actions를 통해 빌드, 테스트, 정적 분석, 의존성 검사 등을 자동화합니다.

## 8\. 앱·스킬·에이전트별 완료 기준

같은 개발 프로세스를 사용하더라도, 프로젝트의 성격에 따라 평가 기준은 달라야 합니다.

| 프로젝트 유형 | 반드시 확인할 품질 기준 |
|--------|--------|
| **웹/앱** | 기능, UI, API 계약, 접근성, E2E, 오류 처리, 성능, 보안 |
| **CLI/라이브러리** | 설치·실행·배포 재현성, 호환성, 예외 처리, 테스트 |
| **AI Skill** | 호출 조건, 오작동 방지, 출력 정확성, 반복 평가, 호환성 |
| **AI Agent** | 도구 호출 성공률, 작업 성공률, 권한 경계, 비용, 추적, 실패 복구 |
| **MCP 서버** | 스키마 계약, 인증, 권한, 오류 처리, 외부 연동 테스트 |

특히 AI 에이전트와 스킬은 코드가 실행된다는 이유만으로 완성되었다고 판단하지 않아야 합니다.

동일한 평가 데이터셋으로 성공·실패 사례를 반복 테스트하고, 변경 전후에 품질이 유지되는지 확인해야 합니다. 권한을 넘는 도구 호출, 악성 입력에 의한 지침 오염, 민감정보 노출 등도 검증 대상입니다.

## 9\. 사용자 개입은 최소화하되 중요한 승인만 유지

모든 단계를 수동으로 지시하는 방식과 AI에 무제한 자율성을 부여하는 방식 모두 권장하지 않습니다.

**AI가 자율적으로 진행할 작업**

기술 조사, 상세 설계, 개발, 안전한 로컬 테스트, 오류 수정, 리팩터링, 테스트 보완, 문서 갱신, PR 작성 및 수정

---

**사용자 확인이 필요한 작업**

요구사항의 중대한 변경, 민감한 권한 부여, 새로운 비용 발생, 데이터 삭제, 운영 DB 마이그레이션, 실제 서비스 배포 등

독립적인 작업은 최대 2개 정도의 병렬 워커로 시작하고, 공유 파일이나 같은 데이터 구조를 수정하는 작업은 순차적으로 처리하는 것이 좋습니다.

복잡한 프로젝트도 무조건 여러 모델을 동원하기보다, **하나의 주 실행 에이전트가 책임을 유지하면서 필요할 때 전문 워커를 활용**하는 구조가 적합합니다.

## 10\. 프로젝트 메모리와 유지보수 정책

장기 프로젝트는 ChatGPT의 Projects 기능으로 정리합니다. 프로젝트마다 대화, 설계 자료, 지침을 관리할 수 있습니다.

현재 공식 문서에서 특히 주의할 사항은 **프로젝트 전용 메모리를 사용하면 해당 프로젝트에서는 ChatGPT Work를 사용할 수 없다는 점**입니다. 따라서 Work를 중심으로 진행할 프로젝트는 메모리 설정을 확인해야 합니다. citeturn300581search1

또한 다음 운영 원칙을 권장합니다.

| 영역 | 기본 정책 |
|--------|--------|
| 컨텍스트 | 현재 작업에 필요한 문서만 읽기 |

| 작업 크기 | 검토 가능한 작은 PR 중심 |

반복적인 CI 실패 감지나 의존성 취약점 점검은 추후 예약 작업으로 설정해도 좋습니다. 운영 환경에 대한 변경은 검토와 승인 절차를 유지합니다.

이 개발 방식을 앞으로 신규 프로젝트의 기본 권장 방식으로 반영하겠습니다. 단, AI가 작성한 코드의 품질은 실제 빌드·테스트·리뷰 결과로 판단하며, 확인되지 않은 작업을 완료로 처리하지 않는 원칙을 유지하겠습니다.
