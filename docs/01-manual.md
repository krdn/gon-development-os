## Herdr의 탭·분할 터미널·세션·파일 구분

작업 방식, 사용하는 화면, 실행 장소, 모델을 각각 선택하면 인계와 권한 혼동이 줄어든다.

<div><div><span>화면</span><b>Herdr space / tab / pane</b><small>프로젝트 묶음 / 작업 화면 / 분할 터미널</small></div><div><span>대화</span><b>Codex CLI 세션</b><small>같은 결과는 이어가기 · 독립된 작업은 새 대화</small></div><div><span>저장</span><b>프로젝트 문서</b><small>새 세션도 실제 파일을 읽어 인계</small></div></div><p>tmux에서 한 화면을 나누는 단위도 pane입니다. 이 안내는 이를 ‘분할 터미널’이라고 부릅니다. Files·Changes는 보조 패널이며 Codex 대화 자체가 아닙니다.</p><div><table><thead><tr><th>칸</th><th>기획 탭</th><th>개발 탭</th></tr></thead><tbody><tr><td>A</td><td>주 기획 Codex · P1~P5 같은 세션 · 통합 문서 작성</td><td>새 개발 Codex · 문서 읽기 → 구현과 수정</td></tr><tr><td>B</td><td>선택적인 독립 조사 Codex · 지정 notes 파일만 작성</td><td>실행 서버용 쉘 · 로그 확인</td></tr><tr><td>C</td><td>파일 확인용 쉘 · pwd / ls / less</td><td>검사·문서 확인용 쉘</td></tr></tbody></table></div><p>설치본 Herdr app에서 Ctrl+Shift+O로 오른쪽을 나누고, 오른쪽 칸을 선택한 뒤 Ctrl+Shift+E로 아래를 나눕니다. Ctrl+Shift+Z는 선택 칸 확대·복귀, F2는 탭 이름 변경입니다. 개인 키가 다르면 Ctrl+Shift+P 명령 팔레트와 도움말로 확인합니다.</p><p>새 칸은 쉘입니다. <code>codex</code>를 실행해야 새 AI 대화가 시작됩니다. 자연어 요청은 Codex 입력칸, 쉘 명령은 Codex가 실행되지 않은 칸에 넣습니다. 같은 세션을 두 칸에서 동시에 재개하거나 같은 파일을 동시에 수정하지 않습니다.</p>

<p><b>기획 인계:</b> docs/PROJECT-BRIEF.md와 docs/STATE.md를 실제로 읽히고 승인 상태·목표·포함/제외·완료 기준·미정·첫 작업을 요약해 확인합니다. 이미 확정된 결정을 임의로 다시 설계하지 않습니다.</p><div>P1~P5를 진행했다면 기획 문서와 근거를 읽고 확정·제안·미정을 확인한다. 아래 예시보다 실제 결정을 우선하며 조사나 문서를 중복 생성하지 않는다. 문제·수요·대안이 불명확하면 <a href="#planning-1">P1 문답·리서치</a>로 돌아간다.</div><div><b>작업 위치</b> Herdr 개발 A의 같은 Codex 세션</div><h3>사용자가 준비할 것</h3><p>대상 사용자, 가장 불편한 문제, 제공할 입력·원하는 결과를 설명한다. “반드시 필요한 것”과 “나중에 해도 되는 것”을 구분한다.</p><h3>AI가 수행할 순서</h3><ol><li>사용자 문제를 한 문장으로 정리하고 대표 사용 흐름을 3–5개 행동으로 적는다.</li><li>첫 출시의 최소 유효 범위(MVP)와 제외 범위를 나눈다. 미래 요구를 현재 기능에 섞지 않는다.</li><li>수용 기준을 관찰 가능한 입력·행동·결과로 쓴다. 정확도·성능 같은 목표는 측정 대상과 방법까지 정한다.</li><li>확정 결정·제안·미정을 구분한다. 구현에 당장 필요하지 않은 미정은 이유와 다음 확인 시점을 남긴다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>PRODUCT 또는 기존 요구사항 문서</li><li>기능별 수용 기준</li><li>비범위·미정 목록</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>첫 사용 흐름과 성공·실패 기준을 구체적으로 설명할 수 있으면 G1 통과. 세부 미래 기능까지 확정할 필요는 없다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>[아이디어]를 첫 출시 가능한 범위로 정리해줘.
대상 사용자, 문제, 입력과 출력, 대표 사용 흐름,
이번 범위와 제외 범위, 관찰 가능한 수용 기준을 작성해줘.
확정·제안·미정을 구분하고, 개발을 막는 질문만 먼저 확인해줘.</pre></div><div><b>예시</b><p>“사진 1장 업로드 → 인식한 텍스트 확인 → 사용자가 수정 → 저장”을 첫 범위로 잡는다. 해설 생성·결제·대량 처리는 별도 작업으로 미룰 수 있다. 이는 설명용 예시이며 실제 프로젝트 결정은 요구에 맞춰 정한다.</p></div><p><b>막히면</b> “좋게”, “빠르게”, “정확하게”만 있으면 대표 입력과 기대 결과를 추가한다. 데이터 없이 정확도 목표를 달성했다고 가정하지 않는다.</p>

## 03 구조와 상태 흐름을 설계한다

작은 기능 하나가 화면·서버·데이터를 통과하는 경로와 실패했을 때의 동작을 정한다.

<div><b>작업 위치</b> Herdr 개발 A의 Codex CLI · 웹 구현이면 gon-web-engineering 관련 지침</div><h3>사용자가 준비할 것</h3><p>유지해야 할 기술·외부 연동·운영 제약을 알려준다. 기존 프로젝트라면 현재 API·DB·인증 방식이 기준이다.</p><h3>AI가 수행할 순서</h3><ol><li>관련 코드와 기존 구조를 읽고 변경할 경계를 찾는다. 새 프로젝트의 기술은 실제 요구를 기준으로 선택한다.</li><li>입력, 검증, 처리, 저장, 결과 반환을 연결하고 API·데이터 구조의 책임을 구분한다.</li><li>빈 상태·대기·처리 중·성공·실패·재시도와 새로고침 후 복구를 필요한 만큼 설계한다.</li><li>중요한 선택의 이유와 대안을 짧게 기록한다. 구조 결정이 바뀔 때만 결정 기록(ADR)을 남긴다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>ARCHITECTURE 또는 기존 구조 문서</li><li>화면·API·데이터의 계약과 상태 흐름</li><li>확정 기술과 남은 기술적 미정</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>첫 기능의 입출력과 주요 오류 처리 방식이 정해지면 04로 간다. 전체 제품을 미리 세밀하게 설계할 필요는 없다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>확정한 MVP와 현재 저장소를 기준으로 첫 기능의 구조를 설계해줘.
화면·API·데이터 경계, 정상 흐름과 오류·재시도 흐름을 포함해줘.
기존 기술과 계약은 보존하고 변경이 필요한 이유를 기록해줘.
웹 작업이면 gon-web-engineering의 해당 지침을 적용해줘.</pre></div><div><b>예시</b><p>신규 웹에서 기술이 미정이면 현재 웹 스킬은 React/TypeScript + Rust(Axum/Tokio) + PostgreSQL(SQLx)를 기본안으로 둔다. 기존 C#·Python 프로젝트를 이 조합으로 자동 변환하지 않는다.</p></div><p><b>막히면</b> 외부 API나 인증 조건이 불명확하면 관련 계약을 먼저 확인한다. 조사만으로 접근 권한이나 실제 호출 성공을 확보했다고 기록하지 않는다.</p>

## 04 문서와 실행 환경을 연결한다

다음 채팅에서도 같은 기준을 읽고 같은 검사를 실행할 수 있게 만든다.

<div><b>작업 위치</b> 실제 프로젝트 폴더를 연 Codex · 기준 GitHub 저장소</div><p>GitHub 저장소를 관리 기록의 기준으로 삼고 기능별 적용·불가·대체 기록을 관리 문서에 남긴다. 로컬 준비만 허용되거나 접근할 수 없으면 pending_sync로 구분한다.</p><h3>사용자가 준비할 것</h3><p>저장할 위치를 정한다. 새 원격 저장소 생성이 필요한 경우 이름과 공개 범위를 명확히 한다. 기존 프로젝트는 기존 문서·CI를 유지한다.</p><h3>AI가 수행할 순서</h3><ol><li>일반 프로젝트와 AEOS 구조 중 현재 상황에 맞는 한 가지를 선택한다. 같은 내용을 두 문서 체계에 중복 작성하지 않는다.</li><li>기존 문서가 없고 필요할 때만 AGENTS·README·PRODUCT·ARCHITECTURE·PLAN·STATE와 GitHub 관리 매핑을 구성한다. AI가 실제 내용과 명령을 채운다.</li><li>매니페스트·잠금 파일·CI에서 실제 설치·실행·검사 방법을 확인하고 실행 가능한 최소 환경을 만든다.</li><li>착수 전 검사 결과를 기록해 기존 실패와 새 회귀를 구분한다. 비밀값 대신 안전한 설정 방법만 문서화한다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>문서 진입점과 실제 프로젝트 기준 문서</li><li>실행·검사 방법과 초기 결과</li><li>첫 작업의 선행 환경 조건</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>다음 작업자가 문서 위치를 알고 필요한 명령을 실행할 수 있으면 05로 간다. 틀 생성만으로 내용 구성이 완료되지는 않는다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>이 프로젝트의 기존 문서와 개발 환경을 기준으로 작업 기반을 정리해줘.
같은 역할의 문서를 중복 생성하지 말고 필요한 내용만 보완해줘.
실제 설치·실행·검사 명령을 확인하고 기준선 결과를 기록해줘.
앱 구현까지 요청된 범위이므로 문서 정리 후 첫 기능으로 이어가줘.</pre></div><div><b>예시</b><p>일반 프로젝트는 docs/PRODUCT.md 등에 기록한다. .ai/contracts·.ai/tasks·scripts/aeos.py가 보이면 AEOS 도입 상태를 확인하고 기존 체계를 이어 쓴다.</p></div><p><b>막히면</b> 문서 생성기가 기존 파일을 감지하면 내용을 읽어 직접 연결한다. 경로 충돌·심볼릭 링크는 의도한 물리 경로를 확인한다. 설치되지 않은 명령을 실행 가능한 것으로 적지 않는다.</p>

<a id="step-05"></a>

## 05 첫 작업을 검증 가능한 크기로 나눈다

한 번의 변경으로 관찰할 수 있는 결과를 정하고 구현 범위를 고정한다.

<div><b>작업 위치</b> Codex · GitHub Issues/Projects · AEOS 계약 링크</div><p>기존 이슈를 재사용하고 Project 상태·담당·라벨·Milestone을 실제 기준에 맞춰 연결한다. 업무 분해는 sub-issues, 선행 차단은 dependencies로 관리하며 지원 불가면 이슈 링크로 대체한다.</p><h3>사용자가 준비할 것</h3><p>가장 먼저 확인하고 싶은 사용자 행동을 고른다. AI가 제안한 순서에서 목표를 바꿀 필요가 있는지만 판단하면 된다.</p><h3>AI가 수행할 순서</h3><ol><li>첫 기능의 입력·출력·허용 변경·제외 범위를 명시한다.</li><li>선행 작업과 완료 조건을 적는다. 검증 방법이 없는 조건은 관찰 가능한 기준으로 바꾼다.</li><li>버그는 수정 전에 실패 조건을 재현하고 정상 동작 기준을 기록한다.</li><li>독립 작업의 위임이 명시적으로 요청되거나 적용 지침이 요구하는 경우에만 소유 파일과 통합 담당자를 정한다. 기본은 현재 AI가 직접 수행한다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>구체적인 첫 작업과 검사 방법</li><li>관련 파일·자료·기준 revision</li><li>작업 순서와 제외 범위</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>무엇을 바꾸고 무엇을 관찰하면 끝인지 분명하면 G2 통과. 구현을 요청했다면 여기서 멈추지 않고 06으로 간다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>첫 작업을 [사용자 행동]으로 잡고 구현해줘.
입출력, 허용 변경, 제외 범위와 수용 기준을 먼저 짧게 정리해줘.
각 기준을 확인할 검사 방법을 연결하고 관련 범위만 수정해줘.
버그라면 수정 전 실패 조건부터 확인해줘.</pre></div><div><b>예시</b><p>“업로드 화면만 만들기”보다 “허용된 사진을 업로드하면 저장된 결과를 조회하고, 잘못된 형식은 거부하기”가 연결 상태를 검증하기 쉽다.</p></div><p><b>막히면</b> 한 작업이 여러 독립 사용자 목적을 담고 있으면 나눈다. 파일 수가 적다는 이유만으로 작은 작업이라고 판단하지 않는다.</p>

<a id="step-06"></a>

## 06 작은 기능을 끝까지 구현한다

사용자 행동 하나가 실제 결과로 이어지도록 필요한 구성만 구현한다.

<div><b>작업 위치</b> Herdr 개발 A의 Codex CLI · 같은 실제 폴더와 브랜치</div><h3>사용자가 준비할 것</h3><p>구현 중 새 요구를 추가할 때는 “이번 범위에 포함”인지 “후속 작업”인지 알려준다. 사소한 구현 선택은 AI가 기존 관례에 맞춰 진행한다.</p><h3>AI가 수행할 순서</h3><ol><li>현재 코드의 진입점과 관련 테스트를 읽고 가장 작은 변경으로 기능을 연결한다.</li><li>프론트엔드·API·저장을 필요한 만큼 함께 구현한다. 임시 화면이나 모의 데이터와 실제 연동을 구분한다.</li><li>기존 스타일·패키지 관리자·API 계약을 유지하고 무관한 정리나 리팩터링을 섞지 않는다.</li><li>작업 중 의미 있는 검사를 실행하고 실패 원인을 좁힌다. 도착한 결과와 다음 확인을 상태에 반영한다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>요청과 직접 관련된 코드 변경</li><li>실행 가능한 첫 사용자 흐름</li><li>모의 처리·미연결·남은 항목의 구분</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>구현된 흐름이 검증 가능한 상태이면 07로 간다. 코드 작성이나 프로세스 시작만으로 기능 완료라고 하지 않는다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>정리한 첫 작업을 구현해줘.
관련 코드·규칙을 먼저 확인하고 기존 변경을 보존해줘.
사용자 행동이 API와 저장 결과까지 이어지게 만들고,
임시 처리나 아직 연결되지 않은 부분은 명확히 표시해줘.
구현 후 관련 검증으로 계속 진행해줘.</pre></div><div><b>예시</b><p>업로드 버튼 → 서버의 파일 형식 검사 → 저장 → 결과 조회를 연결한다. 업로드 성공 문구만 표시하고 저장이 안 되는 상태는 완료가 아니다.</p></div><p><b>막히면</b> 동일 원인이 반복되면 가설을 바꾸고 관찰 근거를 추가한다. 의존 서비스가 막혔으면 가능한 독립 작업을 진행하고 차단 조건을 남긴다. 지연·할당량 때문에 모델을 임의로 바꾸지 않는다.</p>

<a id="step-07"></a>

## 07 실제 동작을 검증하고 수정한다

수용 기준마다 실제로 무엇을 확인했는지 증거를 남긴다.

<div><b>작업 위치</b> Codex · 테스트 도구 · 필요한 브라우저·실제 연동 환경</div><h3>사용자가 준비할 것</h3><p>대표 입력·실패 사례·접근 가능한 시험 환경을 제공한다. 로그인된 사용자 흐름이 필요하면 안전한 인증 경로를 사용한다.</p><h3>AI가 수행할 순서</h3><ol><li>변경에 맞는 빌드·타입 검사·테스트를 실행한다. 명령은 프로젝트와 CI의 실제 구성을 따른다.</li><li>정상·빈 입력·잘못된 입력·중복/재시도 등 요구와 관련된 경계를 검증한다.</li><li>UI 변경은 관련 실제 사용자 흐름과 필요한 화면 크기·오류 상태를 확인한다. 적절한 연결 도구를 우선하고 웹 조작은 설치된 브라우저 도구를 사용한다.</li><li>실패 원인을 수정하고 영향을 받는 검사를 다시 실행한다. 테스트 삭제나 기준 완화로 실패를 숨기지 않는다.</li><li>대상 revision·환경·명령·결과·증거 경로를 기록하고 PASS/FAIL/NOT_RUN/UNKNOWN을 구분한다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>수용 기준별 확인 결과</li><li>테스트 로그·화면·출력 등 필요한 증거</li><li>기존 실패와 새 실패, 미검증 환경의 구분</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>필수 수용 기준을 확인했으면 08로 간다. 미실행 검사가 있으면 그 이유와 영향을 남기고 완료 범위를 제한한다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>수용 기준별로 실제 검증을 실행해줘.
정상 흐름과 관련 오류·재시도 흐름을 확인하고,
FAIL은 원인을 수정한 뒤 해당 검사를 다시 실행해줘.
각 결과에 대상 revision, 환경, 명령, 관찰 결과와 증거를 남겨줘.
실행하지 못한 검사는 NOT_RUN, 판단 근거가 부족하면 UNKNOWN으로 구분해줘.</pre></div><div><b>예시</b><p>사진 업로드 후 새로고침해도 결과를 조회할 수 있는지 확인한다. 인증 화면으로 리다이렉트된 것만 확인했다면 로그인 이후 기능과 운영 화면은 미검증이다.</p></div><p><b>막히면</b> 종료 코드 0·HTTP 200·설정 저장을 사용자 흐름 성공으로 확대하지 않는다. 브라우저마다 로그인 상태가 같다고 가정하지 말고 실제로 확인한 세션을 적는다.</p>

<a id="step-08"></a>

## 08 검토하고 변경을 통합한다

요구사항·변경 내용·검증 결과가 서로 맞는지 검토하고 요청된 전달 단계까지 진행한다.

<div><b>작업 위치</b> Codex · 적용되는 외부 리뷰 도구 · GitHub PR·CI</div><h3>사용자가 준비할 것</h3><p>커밋·PR·통합이 이번 요청에 포함됐는지 명확히 한다. 이미 허용한 범위는 다시 승인하지 않아도 된다.</p><h3>AI가 수행할 순서</h3><ol><li>관련 diff를 수용 기준과 비교하고 범위 밖 변경·비밀값·누락된 검사 여부를 확인한다.</li><li>다중 파일 새 기능·구조 변경 또는 재현 가능한 버그라면 완료/커밋 직전에 외부 리뷰를 한 번 수행한다. 현재 외부 리뷰 지침·중앙 설정을 읽고 실제 반환 모델을 확인한다.</li><li>지적은 근거로 수용 또는 기각한다. 수정한 부분은 관련 검사를 재실행한다. 단순 문서·설정 변경에는 외부 호출을 붙이지 않는다.</li><li>허용 범위에서 작업 관련 변경만 stage하고 staged diff를 확인해 커밋·PR을 만든다.</li><li>필수 CI·리뷰를 해당 revision에서 확인하고 허용된 merge까지 진행한다. 최신 변경 이후의 결과인지 확인한다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>변경 목적과 실제 검증을 담은 PR 또는 완료 보고</li><li>실제 리뷰 결과와 미해결 사항</li><li>요청 범위에 따른 커밋 SHA·PR·통합 상태</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>필수 검사·리뷰와 요청된 통합이 확인되면 G3 통과. PR 생성만 했거나 CI가 진행 중이면 그 상태로 기록한다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>현재 변경을 요구사항과 대조하고 적용 지침에 필요한 완료 경계 리뷰를 수행해줘.
리뷰 지적을 근거로 처리하고 수정분을 검증해줘.
이번 작업에 해당하는 변경만 커밋·PR로 전달해줘.
필수 CI와 허용된 통합까지 확인하고 실제 SHA·PR·결과를 보고해줘.</pre></div><div><b>예시</b><p>“업로드 재시도 추가 / 중복 요청 재현 및 회귀 검사 통과 / 배포 미실행”처럼 PR에 최종 변경을 설명한다. 요청한 모델과 다른 리뷰 응답은 동일 리뷰의 통과로 처리하지 않는다.</p></div><p><b>막히면</b> 리뷰 호출 실패는 미완료다. 필수 검사를 실행할 수 없으면 결과와 필요한 조건을 남긴다. 강제 push나 보호 규칙 우회는 일반적인 통합 요청에 포함되지 않는다.</p><p>이슈·PR·해당 SHA의 CI와 리뷰를 연결하고 원격 내용을 다시 읽어 저장을 확인한다. 배포가 수용 기준인 이슈는 merge만으로 자동 종료하지 않는다.</p>

<a id="step-09"></a>

## 09 배포 준비와 실제 배포를 확인한다

배포 가능 상태, 실제 배포 완료, 사용자 기능 확인을 각각 구분한다.

<div><b>작업 위치</b> Codex · 기존 CI/CD · 지정된 실행 환경</div><h3>사용자가 준비할 것</h3><p>대상 환경과 이번 요청이 배포 준비인지 실제 배포인지 알려준다. 새 비용·운영 데이터 변경 등 기존 권한 밖의 결정을 정한다.</p><h3>AI가 수행할 순서</h3><ol><li>설정·의존성·배포 방법·필요한 데이터 변경과 기존 롤백 방법을 구체화한다.</li><li>실제 호스트·프로젝트·Docker context 등 실행 대상을 확인한다. 예전 주소나 기본 context만 믿지 않는다.</li><li>“배포 준비” 요청이면 검토 가능한 변경·실행 절차·롤백 조건까지 준비해 전달한다.</li><li>실제 배포가 허용됐으면 기존 CI/CD 경로로 진행하고 완료 결과·대상 revision을 확인한다. 권한 밖의 마지막 행동만 구체적인 결과를 제시한 뒤 확인한다.</li><li>배포 후 상태 점검과 관련 실제 사용자/API 흐름을 확인한다. 실패 시 승인 범위의 복구 또는 롤백 절차를 따른다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>대상 환경·배포 revision·실행 결과</li><li>핵심 사용자/API 흐름의 확인 결과</li><li>롤백 방법·남은 제한·운영 확인 상태</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>실제 환경에서 요청한 동작을 확인하면 G4 통과. 배포 준비만 요청했다면 그 결과를 완료로 전달하고 운영 확인은 NOT_RUN으로 남긴다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>[환경·서비스]에 이번 변경을 배포하고 실제 동작까지 확인해줘.
대상과 배포 revision, 기존 CI/CD·롤백 경로를 먼저 확인해줘.
이미 허용된 범위에서 진행하고 새로운 권한이 필요한 마지막 행동만 알려줘.
배포 완료와 실제 사용자/API 흐름의 확인 결과를 각각 보고해줘.</pre></div><div><b>예시</b><p>CI가 성공해 이미지가 만들어진 상태, 서버에 그 이미지가 올라간 상태, 사용자가 업로드·조회에 성공한 상태는 서로 다른 증거다.</p></div><p><b>막히면</b> 운영 인증이나 환경 접근이 없으면 “배포 상태 확인 / 사용자 흐름 미검증”처럼 정확히 제한한다. localhost의 성공으로 운영 성공을 대신하지 않는다.</p>

<a id="step-10"></a>

## 10 결과를 기록하고 다음 작업을 잇는다

다음 채팅이 전체 대화를 다시 읽지 않고 현재 파일과 결과를 대조해 이어갈 수 있게 한다.

<div><b>작업 위치</b> Codex · 기준 GitHub 이슈/Project·PR · STATE 요약 · 같은 프로젝트의 문서로 결과 정리</div><h3>사용자가 준비할 것</h3><p>이번 결과가 실제 목적에 맞는지 확인하고 다음 우선순위를 알려준다. 이어서 진행할 때는 프로젝트 경로와 남은 목표를 전달한다.</p><h3>AI가 수행할 순서</h3><ol><li>실제 구현·검증·리뷰·통합·배포 상태를 나눠 기록한다.</li><li>branch/revision·미커밋 변경·증거 위치·남은 문제·실패한 접근과 다음 행동을 짧게 남긴다.</li><li>다음 채팅에서 상태 기록과 현재 Git·코드·필요한 CI를 대조하고 남은 단계부터 재개한다.</li><li>반복 개선은 구체적인 실패와 효과가 확인됐을 때 제안한다. 전역 스킬·설정·메모리를 임의로 수정하지 않는다.</li><li>예약 점검은 사용자가 요청했을 때 안정된 절차를 대상으로 구성한다. 변화가 없거나 같은 차단이면 조용히 종료하고 의미 있는 변화만 알리도록 한다.</li></ol><div><div><h3>받아야 할 결과</h3><ul><li>짧은 현재 상태와 증거 링크</li><li>다음 실행 가능한 작업 하나</li><li>재개 요청문 또는 필요한 인수인계</li></ul></div><div><h3>다음 단계로 가는 기준</h3><p>다음 사람이 작업 위치·남은 일·확인 방법을 알 수 있으면 이번 단위가 끝난다. 미완료 항목은 완료로 바꾸지 않고 이어간다.</p></div></div><div><div><b>그대로 사용할 요청문</b></div><pre>$gon-project-lifecycle
이 프로젝트를 이어서 진행해줘.
기준 GitHub 이슈·Project·PR/CI를 다시 읽고 로컬 요약, 현재 경로·브랜치·변경과 대조해줘.
남은 것이 구현, 실패 해결, 리뷰, 배포 중 무엇인지 정하고 그 단계부터 진행해줘.
이전 작업을 다시 초기화하지 말고, 완료하면 실제 결과와 다음 행동을 갱신해줘.</pre></div><div><b>예시</b><p>“업로드·조회 PASS, 재시도 PASS, PR 통합 완료, 운영 배포 NOT_RUN, 다음은 OCR 연결”이면 다음 작업은 업로드 화면을 다시 만드는 일이 아니다.</p></div><p><b>막히면</b> 기록과 코드가 다르면 현재 관찰된 사실을 기준으로 수정한다. 오래됐다는 이유만으로 무조건 전체 테스트를 반복하지 않고 변경·실패·근거가 사라진 부분을 확인한다.</p><p>로컬 PLAN/STATE·메모리는 기준 GitHub URL과 마지막 확인 시점의 요약이다. 원격 재조회가 되지 않은 기록은 pending_sync로 남기고 저장 완료로 바꾸지 않는다.</p>

<a id="handoff"></a>

## 기획 세션에서 개발 세션으로 문서 인계

중요한 결정을 접근 가능한 문서에 남기고, 받는 쪽이 실제로 읽었는지 확인한다.

<div><div><b>기획 A · 같은 세션</b><span>P1~P4 문답·근거·결정</span></div><i>→</i><div><b>P5 최종 문서</b><span>PROJECT-BRIEF.md + STATE.md</span></div><i>→</i><div><b>개발 A · 새 세션</b><span>읽기 · 요약 · 첫 작업 확인</span></div></div><p>기획 기록은 <code>docs/research/01-problem.md</code>, <code>02-research-plan.md</code>, <code>03-evidence.md</code>, <code>04-decision.md</code>로 이어집니다. P5는 대화를 통째로 붙이지 않고 확정한 요구·근거·완료 기준·미정·첫 작업을 <code>docs/PROJECT-BRIEF.md</code>에 정리합니다.</p><p>예: 사용자 답 U01 → 조사 Q01 → 근거 S01 또는 사용자 확인 U01 → 결정 D01 → 요구 R01 → 확인 기준 AC01. 실제 근거가 없는 칸은 미확인으로 남깁니다. ‘저장했다’는 응답 뒤 파일을 다시 열어 경로와 내용을 확인합니다.</p><div><div><b>새 개발 세션에 보낼 요청</b></div><pre>현재 프로젝트의 docs/PROJECT-BRIEF.md와 docs/STATE.md를 실제로 읽어줘.
목표·첫 범위·제외·완료 기준·미정·첫 작업을 요약해줘.
기획 문서의 승인 상태와 현재 파일이 일치하는지 확인해줘.
자료가 충돌하면 내게 차이를 알려줘. 기술이 미정이면 비교한 뒤 내 선택을 기다려.
아직 구현하지 말고 인계 요약부터 보여줘.</pre></div><h3>세션 선택</h3><p>P1~P5는 같은 기획 대화, 합의한 첫 출시 범위는 같은 개발 대화로 이어갑니다. 예제 R01~R05는 그 안에서 작은 구현·확인 단위로 순환하고, 첫 범위가 끝난 뒤 독립된 다음 범위는 STATE를 저장하고 새 세션을 엽니다. P5 확정 뒤 새 개발 세션은 권장 방식이며 강제 기능은 아닙니다. 중단한 작업은 해당 폴더의 쉘에서 <code>codex resume</code>로 이름·폴더·시각을 확인해 선택합니다. <code>/new</code>는 새 대화, <code>/compact</code>는 현재 대화 요약, fork는 대화의 갈래입니다. 어느 것도 프로젝트 파일을 자동 복제하지 않습니다.</p><p>Herdr 앱 창을 닫아도 core가 살아 있으면 실행이 유지됩니다. pane/tab을 닫거나 core가 종료되면 해당 실행은 끝납니다. 재부팅 후 Codex는 resume, 서버는 실행 명령으로 다시 시작합니다. 저장된 대화와 저장된 파일은 별개이므로 마칠 때 STATE에 세션 이름·현재 상태·다음 작업을 남깁니다.</p><h3>개발 중의 기준 문서</h3><p>PROJECT-BRIEF는 기획 출발점의 기록입니다. 개발 중 PRODUCT·ARCHITECTURE 등이 필요하면 기존 문서를 읽고 연결합니다. 범위를 바꿀 때 현재 기준과 변경 이유를 STATE에 연결하며 서로 다른 요구를 방치하지 않습니다. 기존 AEOS 계약은 우선합니다.</p>

프로젝트 기준은 저장소 문서로, 현재 판단은 실행 증거로 유지한다.

<p>GitHub를 관리 기록의 기준으로 사용한다. 목적·구조·ADR·계약은 저장소 파일, 작업·상태는 Issues/Projects, 구현·검증은 PR/Actions, 전달은 Release/배포에 연결한다. <div><table><thead><tr><th>내용</th><th>일반 프로젝트</th><th>AEOS</th></tr></thead><tbody><tr><td>제품 목적·범위</td><td>docs/PRODUCT.md 또는 기존 명세</td><td>PROJECT.md</td></tr><tr><td>행동·검증 규칙</td><td>AGENTS.md</td><td>AGENTS.md</td></tr><tr><td>구조·인터페이스</td><td>docs/ARCHITECTURE.md</td><td>ARCHITECT.md</td></tr><tr><td>작업 입력</td><td>PLAN/이슈와 관련 문서</td><td>TASK.md + CONTEXT.md</td></tr><tr><td>구현·검증 결과</td><td>STATE/이슈/PR와 증거</td><td>RESULT.md + EVAL.md</td></tr><tr><td>검토·수용 판단</td><td>실제 리뷰·PR 승인 기록</td><td>REVIEW.md + DECISION.md</td></tr></tbody></table></div><h3>첫 작업의 실제 순서</h3><ol><li>자신의 프로젝트 저장소에서 README·PROJECT·AGENTS·ARCHITECT를 읽고 제품 목적에 맞춘다. 템플릿 원본에 제품 코드를 작성하지 않는다.</li><li>도구를 쓸 경우 현재 scripts/aeos.py와 의존 파일, 도움말을 확인한다. 수동 문서 사용은 별도 registry 승격 없이 가능하다.</li><li>사용하지 않은 작업 ID로 여섯 계약의 틀을 만든다. 처음에는 TASK와 CONTEXT만 채운다.</li><li>현재 AI가 계약을 읽고 구현·검증한 결과를 RESULT와 EVAL에 기록한다.</li><li>REVIEW와 최종 DECISION은 실제 독립 검토자 또는 사람이 담당한다. 실제로 없는 승인을 꾸며 쓰지 않는다.</li><li>요청된 커밋·PR·CI·통합·배포를 거쳐 다음 작업으로 간다.</li></ol><div><div><b>AEOS 저장소 루트에서 사용할 명령 형식</b></div><pre>python3 scripts/aeos.py --help

## 문제가 생겼을 때의 복구 순서
