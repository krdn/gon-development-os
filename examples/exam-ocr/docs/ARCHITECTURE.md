# 처리 구조와 데이터 계약

상태: 구현 전 설계. 설치된 라이브러리를 확인한 뒤 검증 가능한 최소 파이프라인을 선택한다.

```text
입력 경로와 명시적 순서
  → 형식·페이지·언어팩 검사와 원본 해시
  → 작업별 임시 폴더에 페이지 준비
  → 원본 이미지 보존 + 한국어/영어 OCR
  → 텍스트 레이어가 있는 PDF 조립
  → 페이지·텍스트·열기 검사
  → PDF·텍스트·보고서를 임시 이름에서 최종 이름으로 확정
```

## 기술 선택

우선 검증 후보는 Python CLI + Tesseract `kor+eng`이며 PDF 처리에는 OCRmyPDF를 평가한다. 현재 이 세션의 Python 환경에는 OCRmyPDF가 없고 Tesseract의 kor/eng/osd는 확인됐다. 전체 개발 시작 시 프로젝트 가상환경에서 버전·외부 의존성·설치 가능성을 확인한다. Python PATH가 다른 환경을 가리킬 수 있으므로 현재 인터프리터도 기록한다.

OCRmyPDF는 스캔 PDF에 검색용 텍스트 레이어를 추가한다([공식 설명](https://ocrmypdf.readthedocs.io/en/latest/)). 이미지 목록은 순서를 유지해 PDF로 만들거나 Tesseract의 PDF 출력을 결합한다. 두 경로를 동시에 구현하지 말고 작은 샘플 검증 후 하나를 확정한다. 새 웹 프레임워크·DB·클라우드 서비스를 도입하지 않는다.

기울기·회전 보정은 원본 시각 내용을 바꿀 수 있으므로 기본은 보존이다. 개선 옵션을 채택하면 전후 렌더링을 비교하고 사용자에게 변경 사실을 기록한다. PDF에 이미 텍스트가 있으면 중복 OCR을 피하는 정책을 실제 도구 옵션과 검사로 확정한다. 암호·전자서명 PDF는 첫 범위에서 처리 거부하고 이유를 알린다.

## 모듈 책임

| 책임 | 내용 |
| --- | --- |
| 입력과 CLI | 인수·형식·파일 존재·입출력 충돌·순서·오류 코드 |
| 변환 | 언어팩·페이지 준비·OCR·PDF 생성·타임아웃·임시파일 정리 |
| 검증과 보고 | 페이지 수·추출 텍스트·원본 해시·검수 플래그·report.json |
| 테스트 | 독립 정답 텍스트·합성 이미지·정상/오류/재실행 사례 |

초기에는 소수 파일로 구현하고 파일 수를 맞추기 위한 추상화를 만들지 않는다. 프로세스 호출은 인수 배열을 쓰고 사용자 파일명을 셸 명령으로 보간하지 않는다. 원본은 읽기 전용으로 다루며 작업별 임시 경로에서 결과를 검증한 후 확정한다.

## 보고서 데이터

```json
{
  "schema_version": 1,
  "input_sha256": [],
  "language": "kor+eng",
  "engine_versions": {},
  "status": "not_run",
  "pages": [],
  "warnings": [],
  "output_pdf": null
}
```

구현 시 각 page에는 원본 인덱스, 출력 인덱스, OCR 상태, 텍스트 파일 위치, 검수 사유를 담는다. OCR 엔진이 제공하는 신뢰 점수는 실제 정확도와 다르다. 점수가 없으면 null로 남기고 임의 점수를 만들지 않는다. 시간 초과·실패·스킵을 빈 텍스트 성공으로 바꾸지 않는다.

## 자료 관리

`data/input/`은 사용자 원본, `data/synthetic/`는 명시적으로 합성한 시험지, `outputs/`는 결과, `evidence/`는 검사 기록이다. 개발 시 이 원본·산출물·임시 경로의 Git 제외 정책을 정한다. 문제 본문은 로그에 전부 출력하지 않으며 메타데이터와 필요한 최소 진단만 남긴다.
