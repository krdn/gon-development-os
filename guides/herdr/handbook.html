① 한 탭을 나누는 방법 · tmux의 pane과 같은 뜻

Herdr의 space는 프로젝트 묶음, tab은 기획·개발 같은 작업 화면입니다. 탭 안을 나눈 각 터미널이 pane(분할 터미널)입니다. Files·Changes는 보조 패널이며 아래 A·B·C와 역할이 다릅니다. Herdr 안에서 tmux를 따로 실행할 필요는 없습니다.

키가 다르면: Ctrl+Shift+P의 명령 팔레트나 Ctrl+Shift+? 도움말에서 실제 단축키를 확인합니다. 이 안내는 설치본 Herdr app 0.1.11의 설정을 확인했습니다. 터미널판 Herdr(TUI)의 Ctrl+B 접두키 안내와 섞지 않습니다.

② 같은 세션·새 세션·resume·fork를 고르는 기준

이 페이지의 번호는 실습 순서입니다. 실행 계약 2.0.0·관리 매뉴얼의 공정과 아래처럼 대응합니다. 실습 요청문은 해당 단계만 수행합니다. 전체 실행을 맡겼다면 승인된 묶음 안에서 각 실습 입력을 기다릴 필요가 없습니다.

하나의 결과를 끝낼 때까지 같은 대화를 기본으로 합니다. 이 안내의 기획 결과는 승인된 개발 시작 문서, 개발 결과는 합의한 첫 출시 범위입니다. 예제의 R01~R05는 같은 세션에서 하나씩 구현·확인합니다. 할 일 앱 완성 뒤 독립된 달력 기능처럼 새 범위를 시작하면 문서로 새 세션을 엽니다. 프로젝트 전체를 무조건 한 대화에 넣거나 단계마다 새 대화를 만들 필요는 없습니다.

지금 상황선택그다음 행동
P1→P2, P3 추가 조사, P4 정정같은 기획 세션A에서 계속 질문하고 해당 단계 파일을 갱신합니다.
독립된 자료 조사 한 건B의 새 세션P1·P2 파일을 읽히고 지정한 notes 파일 하나만 작성합니다.
P5 확정 뒤 구현을 시작새 개발 세션 권장최종 문서와 STATE를 읽혀 요약부터 확인합니다. 기능상 강제 조건은 아닙니다.
방금 만든 기능의 오류 수정같은 개발 세션재현 순서·기대·실제·오류를 이어 보냅니다.
어제 중단한 같은 작업기존 세션 재개쉘에서 codex resume → 이름·폴더·시각으로 선택 → 현재 파일 재확인.
첫 범위 완료 후 독립된 새 범위새 세션쉘에서 codex 또는 기존 Codex에서 /new. STATE·개발 기준 문서를 읽힙니다.
같은 배경으로 다른 접근 비교fork대화를 복사한 새 ID입니다. 파일은 자동 복제되지 않습니다. 다른 결과 파일이나 worktree를 정합니다.
같은 작업인데 대화가 길어짐기록 후 compact중요 결정을 파일에 저장하고 /compact. 같은 대화를 요약해 이어갑니다.

fork 실행: 현재 작업을 마치고 A의 Codex에서 /quit로 쉘에 나온 뒤, 같은 프로젝트 폴더에서 codex fork를 실행합니다. 목록에서 원본 대화를 골라 새 갈래를 시작합니다. 두 대화가 같은 파일을 함께 수정하지 않게 결과 파일 또는 worktree를 먼저 나눕니다.

대화 이름과 ID: /rename 프로젝트-기획, /rename 프로젝트-첫기능으로 구분하고 /status에서 상태·식별 정보를 확인합니다. 두 세션이 있는 폴더에서 --last를 쓰면 의도와 다른 최근 대화를 고를 수 있으므로 기본은 목록 선택입니다.

세션과 파일은 별개입니다. /new로 새 대화를 열어도 폴더의 파일은 그대로입니다. fork는 대화의 갈래이며 Git branch/worktree와 다릅니다. 같은 폴더에서 두 Codex가 동시에 같은 파일을 수정하지 않도록 담당을 나누세요. 동일한 Codex 세션을 두 분할 터미널에서 동시에 진행하지 않습니다.

③ P1~P5의 기록이 최종 개발 문서가 되는 과정

실제 문장은 이렇게 이어집니다

P1·U02/U03: “새로고침 후 남아야 한다. 같은 PC·브라우저에서 쓴다.”

P4·D02: 추가·완료·삭제·새로고침 유지를 포함하고 로그인·동기화는 제외.

P5·R04: 목록과 완료 상태를 같은 브라우저에 저장한다.

P5·AC04: 항목을 추가하고 완료 표시한 뒤 새로고침해도 두 상태가 남는다.

첫 구현 작업: 할 일 추가와 빈 입력 안내부터 구현 → 직접 확인 → 다음 기능.

위 문장은 설명용 예시입니다. 실제 사용자 인터뷰나 완성 앱의 검증 결과가 아닙니다. 실제 프로젝트에서는 내 답변과 확인한 근거로 바꿔야 합니다.

이 예시는 Q03 → U02(새로고침 요구), Q02 → U03(같은 브라우저 제약) → D02 → R04·AC04로 연결됩니다. S01은 미확인이므로 저장 API를 확정하는 근거로 쓰지 않습니다.

최종 문서에는 이 내용이 보여야 합니다

  1. 앞쪽 요약: 무엇을 왜 만드는지, 첫 범위와 제외, 가장 중요한 완료 기준.
  2. 세부 요구: 사용 흐름, R번호별 기능, AC번호별 확인 행동과 기대 결과.
  3. 제약과 결정: 데이터·운영·기술 확정/미정, 근거 링크, 남은 미정과 시작을 막는지 여부.
  4. 출발점: 첫 구현 작업, 승인 상태·실제 날짜·문서 버전, 연결된 STATE.

초안 → 내가 읽고 정정 → 실제 합의 → 승인 기록 순서를 따릅니다. 미정이 있는데 AI가 임의로 “승인 완료”라고 쓰지 않게 합니다. P5의 승인 요청에서 대괄호를 실제 확인 내용으로 바꾸고, 03의 인계 요청을 사용하면 문서로 인계할 수 있습니다.

개발 중에도 PROJECT-BRIEF.md 한 곳에서 범위·요구·완료 기준을 갱신합니다. 별도 PRODUCT를 중복 생성하지 않습니다. 구조 설명이 필요한 경우에만 ARCHITECTURE.md를 추가합니다. 기존 명세가 있다면 그 경로를 유지하고 STATE는 현재 버전·변경 근거·다음 행동을 연결합니다.
