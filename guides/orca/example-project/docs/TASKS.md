# 작업 계획 — 개인 할 일 앱 학습 예시

기준: [PROJECT-BRIEF](PROJECT-BRIEF.md). 실제 GitHub 이슈/Run/Task/Dispatch: 아직 없음.

| 작업 | 선행 | R / AC | 담당 파일 범위 | 결과 증거 |
| --- | --- | --- | --- | --- |
| K00 기술·저장 제약 확인 | 실제 범위 확인 | R04 / AC04 전제 | PROJECT-BRIEF의 미정 절만 주 조정자가 갱신 | 공식 출처와 사용자 선택 |
| K01 추가·빈 입력 | K00의 환경 결정 | R01·R05 / AC01·AC05 | 실제 구조 확인 후 UI·관련 시험 파일 지정 | 정상/공백 입력 실제 실행 |
| K02 완료·해제·삭제 | K01 통합 | R02·R03 / AC02·AC03 | 실제 구조 확인 후 지정 | 선택 항목 상태 변경·삭제 |
| K03 저장·복원 | K01 통합 + 저장 제약 확정 | R04 / AC04 | 저장 모듈·연결 지점·관련 시험 파일 지정 | 새로고침 후 항목·상태 비교 |
| K04 통합 확인 | K02·K03 | AC01~AC05 | 필요한 통합 수정과 검증 기록 | 한 커밋에서 전체 흐름 시험 |

이 작은 예제는 공통 화면 파일이 겹칠 수 있으므로 기본은 K01→K02→K03 순차 구현이다.
코드 구조를 분리해 파일 책임이 겹치지 않는 것이 확인된 경우에만 K02/K03을 병렬로 진행한다.
별도 worktree를 써도 의미 충돌이 자동 해결되는 것은 아니다.

각 작업 지시에는 기준 커밋·읽을 파일·독점 수정 파일·금지 범위·검증 방법을 추가한다.
작업자는 변경·시험·커밋·PR을 보고하며 주 조정자가 통합 문서를 갱신한다.

GitHub 연결 후 작업 상태의 기준은 Issues/기존 Projects이며, 이 파일은 실제 URL과 Orca 작업의 대응 요약으로 유지한다. 연결되지 않았다면 pending_sync 또는 아직 없음으로 구분한다.
