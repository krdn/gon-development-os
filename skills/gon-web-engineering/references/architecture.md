# 신규 웹 프로젝트의 기술 구성

읽을 때: 신규 프로젝트 생성, 기술 선택, 공통 구조 또는 배포 구조를 결정할 때.

## 적용 범위

이 문서는 AI가 설계·구현·수정·검증을 주도하는 장기 운영 웹 서비스, SaaS, 업무 시스템의 기본안이다. 모든 종류의 소프트웨어에 대한 절대적인 성능 순위를 뜻하지 않는다.

현재 사용자의 명시적 요구, 기존 저장소의 확정된 결정과 운영 제약을 반영한다. 기존 프로젝트를 이 기본안에 맞추기 위한 재작성은 별도의 요구가 있을 때만 진행한다.

## 기본 조합

| 영역 | 기본 선택 |
| --- | --- |
| 화면 | React + TypeScript, strict 모드 |
| 라우팅·빌드 | React Router Framework Mode + Vite |
| 로그인 중심 업무 화면 | SPA와 정적 웹 배포 |
| 업무형 UI 부품 | 기존 체계를 우선하며, 신규 선택에서는 MUI를 검토 |
| 서버 | Rust 안정 버전 + Axum + Tokio |
| 관계형 데이터 | PostgreSQL + SQLx |
| API | Rust DTO/선언 → utoipa OpenAPI → TypeScript 타입/클라이언트 생성 |
| 검증 | Rust 검사, TypeScript 검사, 실제 DB 통합 테스트, Playwright |
| 관측 | 구조화된 로그, 요청 추적, 필요한 성능 지표 |
| 배포 | 하나의 모듈화된 Rust 애플리케이션, 정적 웹 파일, DB |

버전은 프로젝트 생성 시 지원 상태와 상호 호환성을 확인해 선택한다. 사용 버전과 잠금 파일을 기록하고, 안정 버전 업데이트를 정기적으로 검토한다. 최신이라는 이유만으로 사전 릴리스를 기본값으로 선택하지 않는다.

## 구조 원칙

1. 화면, 업무 규칙, API 계약, DB 접근, 외부 서비스 연결의 책임을 구분한다.
2. 처음에는 모듈로 기능을 나누고 하나의 백엔드 배포 단위로 시작한다. 독립 확장·장애 격리의 실제 요구가 생기면 서비스 분리를 평가한다.
3. 업무 규칙과 권한 판단의 최종 구현은 서버에 둔다. 화면의 표시·입력 보조 검증과 구분한다.
4. 초기에는 정적 웹과 API를 같은 출처에서 제공하는 구성을 우선 검토한다.
5. 공개 콘텐츠의 검색 노출·초기 HTML·서버 렌더링이 핵심이면 렌더링 방식을 재평가한다. 추가 렌더링 서버의 운영 비용을 포함한다.
6. 캐시, 작업 큐, 파일 저장소는 해당 기능의 부하·내구성·처리 시간 요구에 맞춰 추가한다.
7. 작은 구현 단위를 유지하고 필요한 도구를 표준화한다. AI가 작성한다는 이유로 복잡도를 늘리지 않는다.

## 선택을 조정하는 조건

- 짧은 출시 일정과 잦은 기능 실험이 우선이고 서버 요구가 단순하면 TypeScript 풀스택을 평가한다.
- SQL Server, 기업 인증, 기존 Microsoft 시스템 연계가 중요하면 기존 DB와 ASP.NET Core 조합을 평가한다.
- 프런트엔드도 Rust가 필수이면 Leptos + Axum을 평가한다. 웹·데스크톱·모바일 UI 공유가 목표이면 Dioxus를 검토한다.
- 다른 선택이 필요하면 요구사항, 채택 근거, 유지보수 영향을 저장소의 기존 의사결정 기록 방식에 남긴다. 일상적인 구현 선택에 불필요한 승인 절차를 만들지 않는다.

## 판단 기준

API 지연과 오류율, CPU·메모리, DB 대기, 실제 화면 반응, 변경 검증 시간, 업그레이드·복구 가능성을 함께 본다. 측정하지 않은 성능 우위나 언어별 AI 수정 정확도를 사실로 단정하지 않는다.
