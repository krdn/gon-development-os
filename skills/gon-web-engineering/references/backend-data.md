# 백엔드·DB·API 지침

읽을 때: Rust 서버, 인증·권한, API 계약, SQL, DB 스키마, 마이그레이션을 구현·수정·분석할 때.

## Rust 서버

- 신규 기본 조합은 Rust 안정 버전 + Axum + Tokio다. 실제 매니페스트·잠금 파일·툴체인에 맞는 API를 사용한다.
- 요청 처리, 업무 규칙, DB 접근, 외부 서비스 연결을 구분한다. 작은 함수와 명확한 타입·오류를 사용한다.
- 정상적으로 발생 가능한 실패는 명시적으로 처리하고, 사용자 응답과 내부 진단 정보를 구분한다.
- clone, Arc, Mutex, unwrap, expect를 단순히 이름만으로 금지하거나 허용하지 않는다. 실제 소유권, 복사 비용, 동시성, 복구 가능성을 검토한다.
- 복잡한 제네릭, 커스텀 매크로, 동기화를 추가하기 전에 더 단순한 구현으로 요구를 충족할 수 있는지 확인한다.
- CPU 집중 작업과 blocking 호출이 async 요청 처리를 막지 않도록 실행 위치와 병렬도를 관리한다. 타임아웃·취소·재시도의 의미를 명확히 한다.
- 요청 식별자와 구조화된 진단 정보를 남기되 비밀키와 민감정보를 로그에 포함하지 않는다.

## 서버의 책임

- 인증, 데이터별 접근 권한, 최종 업무 검증은 서버에서 수행한다.
- DB 접속 정보, 비밀키, 서버 전용 라이브러리는 브라우저에 전달하지 않는다.
- DB 엔터티와 외부 응답 DTO를 구분하고, 필요한 데이터만 응답한다.
- 트랜잭션 경계, 중복 요청, 동시 갱신, 외부 서비스 실패를 해당 기능의 요구에 맞게 처리한다.

## API 계약

기본 흐름은 Rust DTO와 API 선언 → utoipa OpenAPI → openapi-typescript → openapi-fetch다.

1. 계약의 기준은 서버 DTO와 API 선언이다. 생성된 프런트 타입은 생성 절차로 갱신한다.
2. API 변경 시 OpenAPI와 TypeScript 타입을 재생성하고, 실제 응답과 계약의 일치를 확인한다.
3. 자동 생성은 런타임 검증, 업무 규칙, 권한, 구버전 클라이언트 호환성을 대신하지 않는다.
4. 이미 열린 브라우저, 외부 API 소비자, 이전 배포 버전과의 호환성을 고려한다.
5. 큰 정수 식별자, 금액, 날짜·시간대의 전송 형식을 명확히 정한다. 양쪽 언어에서 같은 의미로 처리되는지 실제 직렬화 예로 확인한다.
6. 클라이언트에 노출할 오류 형식과 상태 코드를 일관되게 관리한다.

## PostgreSQL과 SQLx

- 기존 DB 제약이 없는 신규 관계형 서비스의 기본은 PostgreSQL + SQLx다.
- 기존 SQL Server 연계나 운영 자산이 요구되면 해당 조건에 맞춰 선택한다. SQLx를 SQL Server용 기본 드라이버로 가정하지 않는다.
- 정적인 SQL에는 가능한 경우 SQLx query! 계열의 검사를 활용한다. 동적 SQL과 업무 정확성까지 자동 검증되는 것으로 해석하지 않는다.
- 검사에는 적절한 스키마의 DB 또는 준비한 .sqlx 메타데이터가 필요하다. 오프라인 메타데이터를 쓰면 버전 관리하고 CI에서 쿼리·스키마와의 일치를 확인한다.
- SQL 값은 바인딩하고, 동적으로 선택되는 컬럼·정렬 조건 등은 허용된 구조로 제한한다.
- 스키마 변경은 마이그레이션으로 관리한다. 실제 PostgreSQL에서 주요 쿼리, 제약조건, 트랜잭션과 필요한 동시성 시나리오를 확인한다.
- 데이터 규모에 맞는 조회 범위, 페이지 처리, 인덱스를 사용한다. 성능 판단에는 실행 계획·잠금·연결 수 등 실제 관측을 활용한다.
- 데이터 변경의 복구 방법과 이전/새 애플리케이션 버전의 호환성을 고려한다. 운영 DB에 임의의 파괴적 변경을 적용하지 않는다.
