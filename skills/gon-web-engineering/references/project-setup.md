# 프로젝트 구성 절차

## 작업 범위를 확인한다

분석 요청이면 파일을 쓰지 않는다. 새 애플리케이션 생성·개발 환경 구성·공통 지침 적용 요청이라면 지정한 폴더에서 진행한다. 기존 버그 수정에는 지침 초기화를 추가하지 않는다.

프로젝트의 기존 진입점과 하위 지침, 매니페스트, 잠금 파일, 툴체인, CI를 확인한다. 글로벌 기술 선호보다 현재 프로젝트의 확정된 결정을 따른다. 이 확인은 기존 C#·SQL Server 프로젝트에도 적용한다.

## 생성할 주제를 선택한다

| 상황 | 스크립트의 topics |
| --- | --- |
| 합의한 조합의 신규 웹 프로젝트 | architecture frontend backend-data verification |
| 기존 React UI의 지침 적용 | frontend verification |
| 기존 Rust API의 지침 적용 | backend-data verification |
| 다른 스택에 일반 검증 원칙만 적용 | verification |

코드 개발 지침을 배치할 때는 `verification`도 포함한다.

프로젝트가 이미 관리하는 상세 지침이 있으면 그 문서를 유지하고 연결한다. 같은 규칙을 두 곳에 중복 생성할 필요는 없다. 기존 경로 체계가 있으면 고정 경로를 생성하는 스크립트 대신 파일 도구로 기존 문서와 연결을 직접 수정한다.

## 스크립트를 실행한다

스킬 경로를 실제 설치 위치로 해석한다. 현재 폴더를 스킬 폴더로 추측하거나 사용자 홈의 고정 경로를 가정하지 않는다.

`--topics`는 필수다. 작업에 필요한 주제만 명시한다. 먼저 필요한 경우 계획을 확인한다.

```text
python3 <skill-directory>/scripts/configure_project.py --project <project-root> --topics architecture frontend backend-data verification
```

사용자가 신규 프로젝트 구성 또는 지침 적용을 요청한 경우 같은 명령에 `--apply`를 추가한다. 프로젝트 루트가 아직 없다면 사용자가 지정한 새 프로젝트 폴더를 먼저 만든다. Python 3.9 이상이 없다면 아래 생성 규칙을 파일 도구로 적용한다.

스크립트는 선택한 참조 문서의 저장소용 사본, 작은 `AGENTS.md`, `CLAUDE.md`, `docs/ai/project-context.md`를 만든다. 애플리케이션 프레임워크나 의존성을 설치하는 스크립트가 아니다. 기존 파일은 보존하고 병합할 항목을 JSON의 `review_required`로 보고한다.

계획 모드는 파일과 폴더를 만들지 않는다. `--apply`는 트랜잭션이 아니므로 쓰기 도중 실패하면 일부 파일이 남을 수 있다. JSON의 `status`와 파일별 `action`을 확인하고 실패 원인을 해결한 뒤 재실행한다. `applied`라도 `review_required`가 남아 있으면 지침 적용 전체가 완료된 것은 아니다.

## 기존 파일을 병합한다

- 기존 `AGENTS.md`, `CLAUDE.md`, `.claude/CLAUDE.md`, `AGENTS.override.md`를 통째로 교체하지 않는다.
- `AGENTS.override.md`가 적용되는 환경이면 실제 활성 지침에도 필요한 연결을 반영한다.
- 기존 CLAUDE 지침이 루트에 있으면 공통 진입점 연결은 `@AGENTS.md`다. `.claude/CLAUDE.md`에 있으면 `@../AGENTS.md`다. 기존 import·상위 지침과 중복되는지 확인한다.
- 프로젝트에서 이미 다른 문서 경로를 사용하면 기존 경로를 유지한다. 스크립트가 보고한 병합 항목은 실제 내용을 읽고 필요한 부분만 수정한다.
- 동명의 상세 문서가 기존 규칙과 다르면 프로젝트 규칙을 보존한다. 근거 없는 신규 기술 정책으로 덮어쓰지 않는다.
- 전역 홈 설정은 현재 요청에 포함되어 있을 때만 수정한다. 프로젝트 구성을 이유로 개인 스킬·전체 권한·계정 설정을 임의로 변경하지 않는다.

## 프로젝트 결정을 기록한다

`docs/ai/project-context.md` 또는 기존 동등 문서에 다음을 실제 확인한 내용으로 기록한다.

- 선택한 프런트엔드·백엔드·DB, 렌더링 방식, 선택 이유와 예외.
- 버전을 확인할 매니페스트·잠금 파일·툴체인 위치.
- 실제 설치·개발 실행·빌드·검사·테스트 명령.
- API 생성, 인증·권한, DB 마이그레이션, 배포·호환성 제약.
- 적용한 지침의 범위와 필요한 후속 결정. 생성기는 초기 참조 문서의 SHA-256을 기록한다. 이는 출처 비교용이며 버전 복구 수단은 아니다. 복사된 문서 자체를 프로젝트에서 보관한다.

문서가 이미 있으면 갱신할 사실만 반영한다. 문서에 자격 증명이나 비밀키 값을 적지 않는다. 미정인 내용은 미정이라고 기록하며, 생성한 기본안을 확정된 운영 사실로 표현하지 않는다.

## 애플리케이션 구현 요청을 완료한다

지침 구성이 끝난 뒤에도 사용자가 요청한 실제 앱을 구현한다. 생성 시점의 지원 상태와 라이브러리 호환성을 확인하고 잠금 파일을 남긴다. Rust API, React UI, 데이터 저장, 계약 생성과 주요 사용자 흐름을 요구에 맞게 연결한다. 명령과 환경을 실제로 검증한 다음 결과를 보고한다.

실제 기술·버전·DB 없이도 성공한다고 가정한 일괄 설치 명령을 만들지 않는다. 기존 프로젝트 전체를 다른 언어나 프레임워크로 변환하지 않는다.

## 구성 도구를 수정할 때

스킬 폴더에서 `python3 -m unittest discover -s scripts -p 'test_*.py'`를 실행한다. 계획 모드의 무변경, 선택한 주제, 재실행, 기존 파일 보존, Claude 진입점, override, 잘못된 경로의 사전 차단을 확인한다. 도구 검증은 실제 Codex·Claude의 자동 선택 검증을 대신하지 않는다.
