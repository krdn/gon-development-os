# AI 개발·검증 지침

읽을 때: 코드 동작, 빌드, 의존성, API·DB 계약을 바꾸거나 버그를 분석·수정·검증할 때.

## 작업 순서

1. 사용자 요구와 기대 동작을 확인한다. 버그는 재현 조건과 실패 결과를 먼저 파악한다.
2. 실제 소스, 관련 지침, 기존 테스트, 버전과 실행 명령을 확인한다.
3. 변경 범위를 좁혀 구현하고 기존 동작과 외부 계약에 미치는 영향을 검토한다.
4. 변경에 필요한 정적 검사와 실행 검증을 수행한다.
5. 근거가 충분하면 불필요한 검사를 반복하지 않고 결과를 보고한다.

## 검사 명령

README, Cargo.toml, package.json, 툴체인, CI 설정에 실제로 있는 명령과 지원 구성을 사용한다. 패키지 관리자, 테스트 스크립트, DB 접속 정보가 있다고 추측하지 않는다.

신규 프로젝트에서 명령을 정의할 때는 다음 범주를 갖추고, 사람이 찾기 쉬운 문서나 태스크 파일에 기록한다.

| 변경 | 필요한 검증의 예 |
| --- | --- |
| Rust 코드 | 포맷, 컴파일·Clippy, 관련 단위·통합 테스트 |
| TypeScript·UI | TypeScript 타입 검사, 웹 빌드, 관련 화면 흐름 |
| API 계약 | OpenAPI·클라이언트 타입 생성, 실제 응답 검사, 기존 계약 영향 |
| DB·SQL | 마이그레이션 적용, SQLx 검사, 실제 PostgreSQL 테스트 |
| 사용자 흐름 | Playwright로 입력·저장·이동·오류 상태 등 관련 동작 |
| 성능 영향 | 실제 요청·데이터 조건의 지연, 자원 사용 또는 화면 반응 |
| 의존성 업그레이드 | 릴리스 변경 사항, 빌드·계약·주요 사용자 흐름 |

프런트엔드 번들 생성과 TypeScript 타입 검사를 구분한다. Rust의 호스트 빌드만으로 별도 타깃·기능 구성을 검증했다고 주장하지 않는다. 현재 기본안은 React/TypeScript UI이므로 브라우저용 Rust/Wasm 빌드는 기본 필수 검사가 아니다. 실제로 Wasm을 선택한 기능에 한해 해당 검증을 추가한다.

## 가설을 비교할 때

원인 불명 성능 문제나 구조 대안의 비교가 필요할 때 적용한다. 현재 환경·데이터·측정 방법과 기준값을 확인하고 주요 가설의 기각 조건을 정한다. 실패 비용이 큰 가정부터 작은 변경으로 확인하며 비교에 영향을 주는 조건을 맞춘다. 기준값이나 재현 환경이 없으면 추정과 미검증을 구분한다.

추가 개선 목표는 필수 수용 기준과 분리하고 탐색 한도·중단 조건을 정한다. 개선과 함께 정확성·권한·접근성·호환성 등 해당 기능의 필수 기준과 악화 여부를 확인한다. 단순 수정에는 별도 가설·벤치마크 절차를 추가하지 않는다.

## 변환·인식 기능의 품질

OCR·검색·생성·파일 변환처럼 출력 품질이 핵심이면 화면을 다듬기 전에 대표 실제 입력과 독립된 기대 결과로 작은 검사를 한다. 실제 자료가 없으면 제작 사례로 시작하되 실제 입력 품질은 NOT_RUN으로 남긴다. 데모에 정답을 주입한 흐름, API 호출 성공, 실제 출력의 정확성을 구분한다.

정확도·누락·순서·편집성 등 사용자의 목적에 맞는 기준과 표본 범위를 정한다. 정답 작성자는 가능하면 비교할 엔진 출력을 보지 않으며, AI 전사와 사람 검수 여부를 구분한다. 같은 입력·조건에서 후보를 비교하고 결과와 처리 시간을 함께 기록한다. 작은 표본을 전체 성능으로 일반화하지 않는다.

수동 교정이 포함되면 자동 출력의 품질과 교정 후 최종 결과를 따로 기록한다. 사용자 작업 시간 절감이 목표라면 동일 범위·품질의 수작업 기준과 처리·교정·내보내기를 포함한 최종 산출까지의 총 시간을 비교한다. 측정하지 않았다면 인식 속도나 CER 개선만으로 사용자 생산성 향상을 주장하지 않는다. 탐색에 사용한 표본의 결과와 별도 평가용 표본의 결과도 구분한다.

모델의 confidence는 정답 확률로 단정하지 않는다. 점수의 원본·문장 대응을 보존하고 사용자가 수정한 내용에 과거 점수를 그대로 붙이지 않는다. 표시 없음과 검수 완료를 구분한다.

## 테스트의 의미

- 재현 가능한 버그, 중요한 업무 규칙, API·DB 계약을 중심으로 의미 있는 테스트를 작성한다.
- 단순 문구·스타일 변경에는 실제 영향에 맞는 확인을 선택한다. 구현을 그대로 복제하는 테스트와 불필요한 전수 테스트를 늘리지 않는다.
- 기존 기대값은 요구사항의 변화나 기존 테스트의 오류가 확인된 경우에만 바꾸고 이유를 남긴다.
- 테스트 통과를 위해 타입 검사, 권한 검사, 계약 검증을 근거 없이 제거하지 않는다.
- 서버가 권한을 확인하는지, 실제 저장 결과가 맞는지, 화면이 필요한 상태를 표시하는지 구분해 확인한다.

## 브라우저와 운영 진단

화면 작업은 실제 브라우저에서 확인한다. 선택·포커스·스크롤 기능은 내부 offset뿐 아니라 긴 본문과 좁은 화면에서 사용자가 대상 내용을 실제로 볼 수 있는지도 확인한다. 실패하면 Playwright 기록, 콘솔, 네트워크, 서버 로그에서 근거를 수집한다. 브라우저·기기 조합은 지원 범위와 변경 영향에 맞춰 선택한다. 컴파일 성공을 사용자 동작의 성공으로 대체하지 않는다.

## 업그레이드와 배포

버전과 잠금 파일을 관리하고 업데이트를 검증한다. 서버와 웹 자산의 버전, 기존 클라이언트, DB 마이그레이션의 관계를 확인한다. 배포와 운영 환경 변경은 현재 작업에서 허용된 범위와 실행 환경의 권한을 따른다.

## 완료 보고

GitHub 관리 문서가 정한 기존 이슈/Project·PR/CI를 갱신한다. 로컬 상태 문서는 기준 원격 URL과 마지막 확인 시점의 요약으로 유지한다. lifecycle 스킬을 사용할 수 있으면 공통 GitHub 절차를 재사용한다. 없으면 아래 연결 기준과 프로젝트별 규칙을 따른다. 기존 항목·본문·상태를 먼저 읽고 필요한 부분만 갱신하며, 생성/갱신 timeout은 재조회하기 전 반복하지 않는다.

| 변경 | 원격에 연결할 검증 증거 |
| --- | --- |
| UI | 관련 이슈/PR, 실제 화면 흐름·상태·뷰포트, 정제된 screenshot/trace와 검사 SHA |
| API | 계약 변경·생성 결과 경로, 호환성 판단·실제 요청/응답의 정제된 증거 |
| DB | migration 경로·적용/롤백 조건, 실제 테스트 대상 환경과 결과. 데이터/연결 비밀값 제외 |
| CI·배포 | 실제 검사 SHA·실행 URL·결과, 배포 revision·환경·사용자 흐름·롤백 조건 |

미실행 검사는 NOT_RUN으로, 원격 미저장은 pending_sync로 구분한다. PR/CI/원격 문서를 다시 읽어 URL·상태·본문·SHA가 맞는지 확인한다. UI 이미지·trace에는 계정/개인정보·세션값이 포함될 수 있으므로 필요한 부분만 정제해 저장한다. 만료될 artifact의 장기 요점·해시는 저장소 문서/허용된 Release asset에 보존한다. merge가 곧 배포 완료인 것으로 이슈/Project를 종료하지 않는다.

무엇을 왜 바꿨는지, 실행한 검사와 결과, 확인하지 못한 범위, 필요한 운영상 고려 사항을 간결하게 보고한다. 실제로 실행하지 않은 검사·배포·설치를 완료했다고 말하지 않는다. 다음 작업에 필요한 결정은 저장소의 기존 문서에 남기고 이 진입점에 작업 이력을 계속 누적하지 않는다.
